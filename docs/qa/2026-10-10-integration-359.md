# #282·#284 최종 통합 검증 (#359)

2026-10-10. PR #349(#284 요청 세대·staging·출력 수용), PR #353(#282 쓰기 전 확인·백업·조건부 복구),
PR #357(#281 생성 출력 신원), PR #358(#292 실제 흐름 회귀)이 모두 들어간 develop에서 #282·#284의 원래 완료 조건을
다시 확인했다. 제품 코드(`src/`)·스키마·규약 버전은 바꾸지 않았다. 결함은 고치지 않고 재현과 함께 아래 5절에 적었다.

**결론: #282·#284 부모 이슈는 아직 닫지 않는다.** 같은 파일 이름을 다시 쓴 새 프로젝트가 옛 프로젝트의 ID·생성 자리를
이어받는 #357의 남은 한계가 그대로이고(조건 2 미충족), 이 때문에 #282 감사 보강의 "다른 프로젝트의 같은 이름 파일을
수정 대상으로 삼지 않는다"가 충족되지 않는다. 나머지 조건은 fixture·브라우저 실측·실제 경과로 충족을 확인했다.
실제 모델 실행은 하지 않았다.

## 4. recovery-provenance Windows 실패 조사 (docs/28 5절 4번)

**실패 위치.** 수정 전 스크립트를 처음 세 번 실행해 세 번 모두 `settle()`의
`getByRole('radio', { name: '백업 후 덮어쓰기' }).check()`에서 15초 timeout으로 끝났다. Playwright 로그는
`<div class="fixed inset-0 z-[100] … bg-surface-sunken/80"> intercepts pointer events`였다 — 저장 충돌 대화상자의 바깥 틀이다.

**원인.** 환경 문제가 아니라 fixture의 두 탭 준비 순서 경쟁이다. 두 탭이 같은 `shop.json` 자동저장 키를 쓴다.
`specAutosave.ts`는 파일 이름을 받는 순간 공용 저장소의 값을 기준(`baseline`)으로 읽고, 500ms 디바운스 뒤 처음 쓴다.
뒤 탭이 앞 탭의 첫 쓰기 **전에** 같은 이름을 받으면 기준이 `null`이고, 앞 탭이 쓰는 순간 `storage` 이벤트에서
기준과 저장값이 달라 뒤 탭이 "다른 탭에서 이 프로젝트를 변경했습니다"로 멈춘다(두 탭 내용이 같아도 그렇다).
원래 스크립트는 앞 탭 준비 뒤 약 0.57~0.67초에 뒤 탭 준비를 끝내 이 500ms 창의 경계에 있었다. 부하·캐시에 따라 어느
쪽으로든 갈 수 있어 Windows 전용 결함으로 볼 근거가 없다.

**대조군.**

| 실행 | 결과 |
|---|---|
| 수정 전, 첫 3회 | 3/3 실패(위 위치) |
| 수정 전, 이후 반복(유휴·Vite 캐시 삭제·vitest 전체를 함께 돌린 부하) | 모두 통과 — 순서가 우연에 달렸음을 보인다 |
| 순서 고정: 두 탭을 먼저 연 뒤 각각 준비(임시 사본) | **수정 전 3/3 실패**(같은 위치·같은 가로막힘), **수정 후 3/3 통과** |
| 앞 탭 CPU 20배 제한(CDP `Emulation.setCPUThrottlingRate`) | 수정 전에도 3/3 통과 — 디바운스는 타이머 기준이라 CPU 제한으로 창이 바뀌지 않는다 |
| 같은 순서만 떼어 낸 최소 재현(두 탭 열기 → 같은 이름 준비 → 1.5초) | 앞 탭 `paused:false`, 뒤 탭 `paused:true, reason:"remote"`, 대화상자 "다른 탭에서 이 프로젝트를 변경했습니다" |

**수정(테스트 측만).** 각 탭을 준비한 뒤 그 탭의 내용이 공용 자동저장에 반영될 때까지(`persistenceStatusStore`의
`draft.shared === true`) 기다리고 다음 탭을 연다. 시나리오 시작 전 두 탭 모두 저장 충돌로 멈추지 않았음을 단언해, 순서가
또 어긋나면 라디오 timeout 대신 `fixture: save conflict dialog`로 바로 실패한다. 수정 후 원래 순서로 7회(그중 3회는 vitest 전체 실행 부하 중) 모두 통과했다.

**남은 제한.** Linux에서 실행하지 못했다. 필수 묶음(`run-journeys.sh`)에는 넣지 않았다 — 넣을지는 PR CI에서 Linux 결과를
본 뒤 정한다. 같은 내용인데도 멈추는 제품 동작 자체는 5절 4번에 따로 적는다.

   앱 밖에서 `shop.json`을 지우고 같은 이름으로 새 문서를 만든 상황(`loadSpec` + 같은 `fileName`) → 재생성.
   관찰: 요청 `generatedRoot`가 옛 `shop/page1`, 프로젝트 ID 동일. 확인 화면에서 Header는 `foreign`이 아니라 `modified`(같은
   프로젝트의 수동 수정)로, 옛 프로젝트의 마지막 생성 Card는 `owned`로 분류돼 **묻지 않고 바뀐다**(백업은 원본 L 바이트로 남고
   되돌리기로 복구된다 — 같은 파일의 안전 범위 테스트). 같은 내용으로 다시 만들면 Export가 옛 프로젝트의 Header·Card를
   **현재**로 보인다. 원인: 스펙 파일에 프로젝트 신원이 없고 `generationTarget.ts`가 `findProjectByFileName`으로 이름에서 ID를
   찾는다. 영향: #282 감사 보강 "다른 프로젝트의 같은 이름 파일을 수정 대상으로 삼지 않는다", #359 조건 2.
   제안 이슈: `fix: 같은 이름으로 다시 만든 프로젝트가 옛 생성 신원을 이어받는다 — 지운 프로젝트의 출력을 묻지 않고 덮고 현재로 표시`
   (스펙 파일에 안정 ID를 두는 해법이면 스키마 변경이라 별도 설계·승인 PR이 필요하다).
2. **이전 프로젝트의 "마지막 적용 되돌리기"가 다른 문서로 바꾼 뒤에도 패널에 남는다(경미).** `ticketStore.compile()`이
   `lastRun`을 지우지 않고 `restoreLastRun`은 호출 시점 세대만 비교한다. 문서를 바꾼 뒤 누르면 이전 프로젝트 파일을
   되돌린다(provenance 확인을 거치므로 지금 프로젝트의 파일·기록은 바뀌지 않는다 — 신규 복사본 테스트가 서로 건드리지
   않음을 단언). 화면에 어느 프로젝트의 적용인지 보이지 않아 맥락이 어긋난다.
   제안 이슈: `fix: 문서를 바꿔도 이전 프로젝트의 되돌리기 버튼이 남는다 — 어느 프로젝트의 적용인지 보이지 않는다`
3. **`unnamed-drafts.mjs:258`가 간헐적으로 30초 timeout된다(테스트 경쟁).** 1차 묶음에서 소유 탭을 닫은 직후 "이어서 열기"를
   한 번만 누르고 `File` 버튼을 기다리다 실패했다. 재실행은 통과. 탭 종료 뒤 Web Lock 해제가 비동기라 그 사이 클릭은
   "다른 탭에서 사용 중"으로 끝나는 것으로 보인다(확정하지 않음). PR #357 기록의 `:247`·`:193` timeout과 같은 계열이다.
   제안 이슈: `test: 초안 소유 탭을 닫은 직후 이어서 열기 여정이 간헐적으로 timeout된다 — 잠금 해제를 기다리지 않는다`
4. **두 탭이 같은 내용으로 같은 파일 이름을 거의 동시에 받으면 뒤 탭이 저장 충돌로 멈춘다(제품 동작, 경미).** 4절 최소 재현.
   기준이 `null`인 탭은 공용 저장값이 자기 내용과 같아도 충돌로 본다. 실제 Open 경로에서 생기는지는 확인하지 않았다.
   제안 이슈: `fix: 같은 내용을 동시에 연 두 탭에서 거짓 저장 충돌이 뜬다 — 기준 없이 시작한 탭이 같은 저장값도 충돌로 본다`
5. **docs/28 갱신 필요.** 5절 4번과 2절 "넣지 않은 스크립트"의 recovery-provenance 설명은 이 수정 뒤 사실과 다르다. 이 PR
   범위(테스트·QA 기록) 밖이라 고치지 않았다.
