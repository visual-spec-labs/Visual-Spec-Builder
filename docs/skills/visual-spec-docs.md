# visual-spec-docs — 설명

`skills/visual-spec-docs/SKILL.md`는 에이전트가 실행 시 참조하는 지시문이다.
사람이 이 스킬이 뭘 하는지 파악하려면 이 문서를 본다.

## 이 스킬이 하는 일

스키마 계약·용어·범위·설계 근거를 물었을 때, **답을 주는 대신 답이 있는 원문의 위치를
알려준다.** 정본 스키마 파일, `docs/`의 각 문서가 어떤 질문에 답하는지, 저장소 밖에서
원문을 받아오는 raw URL을 담고 있다.

핵심은 이 스킬이 스키마 지식을 **일부러 담지 않는다**는 점이다.

스킬에 "`box.width`에는 `fill`, `auto`, 숫자를 넣을 수 있다" 같은 지식을 복붙해두면
당장은 편하다. 그런데 스키마는 버전이 올라가고 필드는 늘거나 준다. 정본이 바뀌는 순간
복붙해둔 줄은 조용히 틀린 것을 가르치기 시작한다. 틀렸다는 신호도 없다 — 에이전트는
그 줄을 그대로 믿고 사용자에게 자신 있게 잘못된 답을 준다.

그래서 이 스킬은 경로만 준다. 답은 매번 파일을 열어서 만든다. 읽지 못했으면 못 읽었다고
말하고, 추측해서 채우지 않는다.

## 언제 실행되는가

`skills/visual-spec-docs/SKILL.md`의 `description`에 적힌 조건과 매칭될 때 자동으로 붙거나,
사용자가 직접 이름을 불러 실행한다.

- "Size에 fill 써도 돼?"
- "스키마 파일 어디 있어?"
- "v0.1에서 뭐가 빠졌지?", "MVP 범위가 어디까지야?"
- "동결됐다던데 바꿔도 돼?"
- 다른 스킬이 작업 중 필드 정의를 확인해야 할 때 (기억에 의존하면 현재 버전과 어긋날 수 있다)

## 어떻게 쓰는가

1. 확인하려는 개념을 한 문장으로 좁힌다. ("`box.width`에 뭘 넣을 수 있나")
2. 에이전트가 필드 판단이면 정본 스키마를, 범위·용어·설계 질문이면 `docs/`의 해당 문서를
   고른다. 어느 문서가 어떤 질문에 답하는지는 `SKILL.md` 본문의 표에 있다.
3. 저장소 안에서 작업 중이면 파일을 읽고, 설치된 사용자 환경이면 함께 설치된 로컬 계약
   (`visual-spec/contract/`)을 읽는다.
4. 읽은 내용을 근거로 답이 나온다.

설치된 사용자 프로젝트에는 `docs/`와 `src/`가 없다. 대신 `visual-spec skills`가 설치한 패키지와
같은 버전의 스키마 3종·문서(05·08·09·11·16)·예제를 `visual-spec/contract/`에 함께 둔다(#278).
네트워크 없이 읽고, 저장소 최신본과 설치본의 버전이 어긋나지 않는다. 로컬 계약에 없는
문서(01~04·06 등)만 GitHub raw URL(기본 브랜치 `develop`)로 읽으며, 그때는 설치본보다 새
내용일 수 있음을 함께 밝힌다.

## 이 스킬이 하지 않는 것

- 스키마 지식 자체를 담아두기 (의도적으로 하지 않는다 — 위 이유)
- 스키마 수정. 무엇이 동결됐고 바꾸려면 어떤 절차를 밟는지는 `docs/06-schema-freeze.md`가 답한다
- 문서 사이트 제공 (없다. 원문은 저장소·로컬 계약에서 읽고, 계약에 없는 문서만 raw URL에서 가져온다)
- 스펙 작성·검증 → [visual-spec-authoring](./visual-spec-authoring.md),
  [visual-spec-validate](./visual-spec-validate.md)가 맡는다

세부 경로 표와 워크플로는 `skills/visual-spec-docs/SKILL.md` 본문을 본다.
어느 스킬로 가야 할지 모르겠으면 [visual-spec](./visual-spec.md) 허브로 돌아간다.
