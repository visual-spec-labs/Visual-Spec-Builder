#282(쓰기 전 수동 변경 보호)는 ["#282 — 재생성 전 수동 변경 보호"](#282--재생성-전-수동-변경-보호) 절, #281(생성 파일의 프로젝트

(`runtime/generation-manifest.json` — 지금 2, #281이 1에서 올림), "`run.json` `protocol`"은 **복구 기록**
(`backups/<runId>/run.json` — 지금 2, #282)이다. 수용 기록 항목의 `ticketProtocol`은 그 출력을 만든 티켓 요청 규약
버전이다.

## 문제

GUI는 에이전트를 실행하지 않는다(#219 A안). 요청 파일을 쓰고, 사용자가 직접 띄운
Claude Code/Codex가 응답 파일과 코드를 쓸 때까지 기다린다. 이 구조에서 두 가지가
비어 있었다.

1. **요청 상태가 뭉뚱그려져 있었다.** 요청 저장·사용자 전달 안내·응답 대기·연결 실패가
   모두 "에이전트 응답 대기 중" 한 줄이었다. 대기는 고정 180초였고 연장할 수 없었다.
   작업공간 서버가 끊겨도 폴링은 조용히 실패하며 "대기 중"으로 남았다.
2. **응답 수용과 출력 파일 수용이 연결되지 않았다.** 취소된 요청의 늦은 응답은
   `requestId`가 달라 버려졌지만, 같은 요청이 늦게 쓴 코드 파일은 `generated/`에 그대로
   떨어졌다. `verifyGenerated.ts`는 파일 존재·참조만 보므로 Export는 4/4·오류 0으로
   성공을 표시했다(2026-10-08 감사에서 실제 Chromium·fixture로 재현).

GUI는 외부 프로세스를 멈출 수 없다. 취소는 **GUI가 기다림을 멈추고 그 요청의 결과를
수용하지 않는다**는 뜻이지, 에이전트가 멈춘다는 보장이 아니다. 이 문서가 정하는 것은
앱이 제어하는 **수용 경계**다.

## 결정 요약

| 항목 | 결정 |
|---|---|
| 요청 신원 | 요청마다 새 `requestId`(UUID). 수동 재시도는 **언제나 새 ID**다. |
| 대기 연장 | 같은 요청의 기한만 바꾼다. `deadline = max(deadline, now + 180초)` — 누적되지 않아 중복 클릭은 한 번과 같다. 끝난 요청은 연장할 수 없다. |
| 재연결 | 폴링이 실패하면 `connectionLost` 단계로 표시하고 계속 기다린다. 복구되면 잠금 소유권을 서버에 다시 확인한다(잃었으면 `lockLost`). 입력 최신성은 수용 시점에 기록한 입력 지문으로 판정한다. |
| 티켓 출력 위치 | 에이전트는 `generated/`가 아니라 요청 전용 임시 출력 `staging/<requestId>/…`에 쓴다(티켓 요청 규약 v2부터). |
| 확정(승격) | 현재 요청·현재 티켓 세대·미취소일 때만 GUI가 임시 출력을 읽어 `generated/`로 옮긴다. |
| 수용 기록 | 확정한 파일마다 요청 ID·페이지·입력 지문·내용 해시를 `runtime/generation-manifest.json`에 남긴다. |
| Export 판정 | 파일·참조 검사(기존)와 별개로 **생성 세대 확인**을 보인다: 현재 / 오래됨 / 부분 / 확인 불가 / 아직 없음. |

## 요청 상태 전이표

자연어(`nl/nlAgentClient.ts`)와 티켓(`ticket/ticketAgentClient.ts`)이 같은 대기 제어
(`ui/agentRequestWait.ts`)를 쓴다. 상태 이름과 취소·timeout·연장의 뜻이 두 통로에서 같다.

### 진행 단계(끝나지 않은 상태)

| 단계 | 뜻 | 화면 문구의 요지 | 근거 |
|---|---|---|---|
| `saving` | 잠금을 잡고 요청 파일을 쓰는 중 | 요청 저장 중 | 요청 PUT 진행 |
| `waiting` · 근거 없음 | 요청 파일 저장 완료. 에이전트가 읽었는지 모른다 | "요청을 저장했습니다. 지시를 에이전트에 전달하세요" + 지시 복사 | 요청 파일 PUT 성공 |
| `waiting` · 출력 근거 | (티켓) 이 요청의 임시 출력 파일이 보인다 | "에이전트가 임시 출력 N/M개를 썼습니다. 응답을 기다립니다" | `staging/<id>/` 목록 |
| `connectionLost` | 폴링이 작업공간 서버에 닿지 않는다 | "작업공간 연결이 끊겼습니다. 복구되면 이어서 기다립니다" | 목록 GET 실패 |
| (응답 처리) | 기다림은 끝났고 응답을 수용 검사·확정하는 중(티켓) | "응답을 받았습니다 — 결과와 출력 파일을 확인하는 중" | 응답 파일 수신 |

**"모델 실행 중"이라는 단계는 없다.** GUI는 에이전트 프로세스·로그를 볼 수 없으므로
확인할 수 없는 사실을 단정하지 않는다. 출력 근거도 "파일이 보인다"까지만 말한다.

## 티켓 출력의 수용 경계

### 왜 staging인가

후보는 네 가지였다. 이슈는 특정 방식을 강제하지 않았다.

| 후보 | 늦은 파일을 막는가 | 정상 결과(B) 바이트를 지키는가 | 비용 |
|---|---|---|---|
| 응답 `requestId` 필터만 | 아니오(현 상태) | 아니오 | 없음 |
| manifest + 해시만 | 감지만 한다 | 아니오 — 같은 경로를 덮는다 | 작음 |
| CAS(쓰기 전 버전 비교) | 외부 writer는 CAS를 거치지 않는다 | 아니오 | 서버 변경 큼 |
| **요청별 staging + 앱 확정 + manifest·해시** | **예(규약을 따르는 에이전트)**, 따르지 않으면 감지 | **예** | 서버 폴더 1개, 규약 v2 |

외부 에이전트의 쓰기는 앱을 거치지 않는다. 그래서 늦은 쓰기를 **막을** 수 있는 유일한
지점은 "어디에 쓰게 하느냐"다. 요청마다 다른 임시 폴더에 쓰게 하면, 취소·만료된 요청이
늦게 쓴 파일은 그 폴더에 남고 앱이 확정하지 않는 한 `generated/`에 닿지 않는다. 확정은
앱 코드 한 곳(`ui/ticketOutputAcceptance.ts`)에서만 일어나므로, 수용 조건을 거기서 강제할
수 있다.

manifest·해시는 규약을 따르지 않는 쓰기(구버전 스킬, 사람이 직접 `generated/`를 고침,
직접 실행한 to-react)를 **감지**하는 두 번째 선이다. 이 경우 바이트를 지킬 수는 없지만,
최신 성공으로 잘못 표시하지는 않는다.

### 확정 조건

티켓 웨이브 응답은 아래를 모두 만족할 때만 `generated/`로 확정된다.

1. 응답의 `requestId`가 이 요청과 같다(기존 `parseTicketResponse`).
2. 응답을 받은 뒤에도 취소되지 않았다.
3. `ticketStore.generation`이 요청 시점과 같다(재컴파일 없음, 기존 #184 검사).
4. `done`으로 보고된 티켓마다 `staging/<requestId>/<filePath>`가 있고 비어 있지 않다.
   없으면 그 티켓은 `failed`("완료 응답이지만 임시 출력이 없다")로 바뀐다 — **부분 도착**.
   응답 또는 staging 일부가 빠지면 이번 웨이브의 확정 후보도 모두 거부하며 기존 정상 파일과 기록을 보존한다.
5. 결과 ID는 중복 없이 이번 웨이브 전체와 정확히 일치한다. 중복·예상 밖·누락은 쓰기 전에 거절한다.
6. staging 읽기·사용자 확인 뒤에도 미취소·동일 세대이며 기존 요청 잠금 소유권을 서버에서 확인했다.
7. (#282) 기존 파일이 마지막 정상 생성 그대로이거나 사용자가 덮어쓰기를 선택했다.
8. 출력·manifest 쓰기는 요청 ID를 보내며 실제 mutation 시점에 CAS와 잠금을 확인한다.
   실패/취소 시 이미 쓴 파일은 유효 lease와 provenance를 확인해 조건부 보상한다. 보상 실패는 복구 경로를 남긴다.

응답 GET 뒤 기한과 취소를 다시 확인하며 티켓 잠금은 출력·manifest 처리까지 유지한다.
중지 또는 재컴파일은 승격 잠금을 즉시 해제 요청하고 후속 파일과 다음 웨이브를 막는다.
긴 확인 대기로 임대가 만료되면 그 요청을 재획득하지 않고 중단한다. 보상은 원래 lease가 유효하면
유지하며, 이미 잃었다면 새 lease와 manifest provenance를 모두 검증한다. undo는 별도 새 lease를 얻는다. 잠금을 얻지 못하면 파일을 건드리지 않고 복구를 미완료로 남긴다.
확정한 파일만 manifest에 기록하며 에이전트의 done 주장만으로는 done이 되지 않는다.

확정 중에도 취소·재컴파일을 확인한다. 임시 파일을 이미 읽었어도 쓰기 전에 취소·세대·소유권을
다시 확인하며, 잠금 해제 또는 새 요청으로 인계된 뒤 오래된 PUT은 서버 mutation 시점에 거부한다.
미확정 티켓은 pending으로 돌아가 재시도할 수 있고 새 계획에는 이전 결과를 반영하지 않는다.
#349 단독 구현의 이미 쓴 파일 미복구 한계는 이 통합에서 #282의 조건부 보상으로 확장했다.
보상도 유효 lease·manifest provenance·CAS를 요구하므로 항상 원자적인 전체 복구를 보장하지는 않는다.
manifest 저장에 실패하면 Export가 확인 불가로 표시할 수 있다.

### 수용 기록(manifest) 형식

`.visual-spec/runtime/generation-manifest.json` — GUI만 쓴다. 에이전트는 쓰지 않는다.

```json
{
  "protocol": 1,
  "entries": {
    "pages/Home.tsx": {
      "requestId": "…",
      "ticketId": "Home",
      "pageId": "home",
      "inputFingerprint": "sha256:…",
      "contentHash": "sha256:…",
      "acceptedAt": "2026-10-10T00:00:00.000Z"
    }
  }
}
```

- `inputFingerprint`는 요청에 실은 페이지(키 정렬 JSON)와 `pageId`의 SHA-256이다. 이번
  범위는 **페이지 단위**다 — 페이지 어디를 고쳐도 그 페이지의 모든 출력이 "오래됨"이 된다.
  컴포넌트 단위 지문과 안정 신원은 #281이 정한다.
- `contentHash`는 확정한 바이트(UTF-8)의 SHA-256이다. 해시는 순수 TS 구현이라 비보안
  컨텍스트(`crypto.subtle` 없음)에서도 같은 값이 나온다.
- 파싱은 예외를 던지지 않는다. 망가진 manifest는 "기록 없음"으로 읽는다(확인 불가 쪽).
- 갱신은 읽고-합치고-쓰기다. 서버 CAS는 `specs/` 전용이라 쓰지 않는다. 두 탭이 같은
  순간 확정하지 않도록 티켓 잠금을 기록 완료까지 유지하고 manifest PUT도 소유권으로 보호한다.
  소유권이 바뀐 오래된 탭의 기록 PUT은 거절한다. 외부 직접 writer와의 CAS는 제공하지 않는다.

### Export 생성 세대 판정

`export/generationManifest.ts`의 `classifyOutputFreshness`(순수 함수). 티켓별 기대 경로와 ZIP에 포함되는 추가 파일마다:

| 티켓 판정 | 조건 |
|---|---|
| `current` 현재 | 기록 있음 · 실제 파일 해시 = 기록 해시 · 기록의 페이지·입력 지문 = 지금 페이지 |
| `stale` 오래됨 | 기록·해시는 맞지만 입력 지문이나 페이지가 다르다(확정 뒤 스펙이 바뀜) |
| `changed` 확인 불가 | 기록은 있지만 실제 파일 해시가 다르다(늦은 쓰기·수동 수정·다른 writer) |
| `unrecorded` 확인 불가 | 파일은 있지만 수용 기록이 없다(직접 실행·구버전 출력) |
| `missing` 없음 | 파일이 없다 |

전체 판정은 위에서부터 처음 맞는 것이다: 모두 `current` → **현재**, 모두 `missing` →
**아직 없음**, `changed`·`unrecorded`가 하나라도 있으면 → **확인 불가**(수용하지 않은
바이트가 현재 파일들 사이에 묻히지 않게 "부분"보다 먼저 본다), `current`가 섞여 있으면 →
**부분**, 나머지(`stale`·`missing`만) → **오래됨**.

파일·참조 검사(4/4·오류 0)는 그대로 보이되 생성 세대 확인과 **따로** 보인다. ZIP
내려받기는 막지 않는다 — 판정은 표시이고, 사용자가 무엇을 받는지 알게 하는 것이 목적이다.

### 결정 요약

| 항목 | 결정 |

| 기준 없는 파일 | 기록이 없으면(`unowned`) 생성기 소유로 **추정하지 않는다** — 직접 실행·구버전 출력·사람이 만든 파일 |

### 판정 표 (`export/overwriteGuard.ts`)

| 판정 | 조건 | 처리 |
|---|---|---|
| `new` | 파일 없음 | 쓴다(백업 없음, 되돌리기는 지우기) |
| `unchanged` | 같은 소유 기록의 해시 = 지금 바이트 = 새 출력 | 쓰지 않는다. 이 요청의 결과로 기록 |
| `owned` | 기록 있음 · 같은 `projectKey`·`pageId` · 바이트 = 기록 해시 | 백업 후 쓴다(묻지 않음) |
| `modified` | 같은 프로젝트·페이지 기록 · 바이트 ≠ 기록 해시 | **확인** |
| `unowned` | 기록 없음 | **확인** |
| `foreign` | 기록의 프로젝트·페이지가 다르거나 모름 | **확인** |

소유권을 먼저 확인하며 동일 바이트만으로 소유권을 얻지 않는다. BOM·줄바꿈만 다른 바이트도 다른 파일로 본다 — 텍스트가 아니라
바이트를 비교하고 백업한다(`readWorkspaceFileSnapshot`).

### 프로젝트 신원(#281과의 경계)

> #281 이후: `projectKey`는 쓰지 않는다. 주인 비교는 수용 기록의 프로젝트 ID(`projectId`)로 하고, 같은 이름의
> 다른 프로젝트·복사본은 생성 자리가 달라 같은 경로를 쓰지 않는다. 아래는 #282 시점의 기록이다.

`projectKey`는 확정 때 열려 있던 프로젝트의 작업공간 파일 이름(`documentStore.fileName`)이다. 안정
project ID가 아직 없어서 쓰는 **임시 키**이고 #281이 정하면 바꾼다. 이름 변경·복사는 확인으로
가고 저장하지 않은 문서는 기록과 맞지 않는다. 그러나 같은 작업공간에서 프로젝트를 삭제하고 같은
파일 이름으로 새 프로젝트를 만들면 기존 기록을 자기 소유로 오판할 수 있다. 따라서 #282의 안정 신원
요건은 **부분 완료**이며 이 PR은 #282를 닫지 않는다. #281의 안정 ID 구현은 별도 작업이다.
외부 프로젝트·기록 없는 파일은 새 출력과 바이트가 같아도 확인 없이 manifest 소유권을 가져오지 않는다.

이 PR이 의존하는 #281 부분 중 최소로 구현한 것은 manifest 항목의 `projectKey` 하나다. 남긴 것:
안정 project/page/component ID, 경로 소유권 재설계(같은 이름 컴포넌트가 같은 `generated/` 경로를
쓰는 구조 자체), Export 생성 세대 판정의 프로젝트 구분(지금 Export는 `projectKey`를 보지 않는다).

### #282 보호 범위

서버의 파일별 원자 쓰기(`writeFileAtomic`)·`specs/` 저장 CAS는 그대로이고, #282는 `generated/`에

더했다. 이것은 **여러 파일 트랜잭션도, 외부 writer 보호도 아니다.**

| GUI 되돌리기 | 파일별 서버 비교로 더 새로운 수정을 덮지 않음 | 같은 파일 |
| 서버 내부 | 같은 서버 안의 쓰기·지우기는 경로별 직렬화(`withWorkspaceMutation`) 후 비교 → rename | 외부 writer가 비교와 rename 사이(아주 짧은 틈)에 쓰면 그 쓰기는 덮일 수 있다 |
| to-react 직접 실행(에이전트) | 스킬 절차(쓰기 전 판정·확인·백업·재비교) — **에이전트가 지키는 약속**이지 강제가 아니다 | 에이전트는 HTTP를 거치지 않고 디스크에 바로 쓴다 |
| 사람·편집기·다른 도구 | 없음. 다음 재생성 때 `modified`/`unowned`로 감지된다 | — |
| 여러 탭 동시 확정 | 파일별 서버 비교가 뒤에 온 쪽을 막는다. 기록(manifest)은 읽고-합치고-쓰기라 한쪽이 빠질 수 있다(#284와 같음 — "확인 불가"로 기울 뿐 거짓 "현재"가 아니다) | — |

중간 실패 보상도 완전하지 않다. 되돌리기 쓰기 자체가 실패하거나(디스크·연결) 그 사이 누가 고쳤으면
그 파일은 새 출력이나 더 새로운 수정으로 남고, 안내 문구가 파일 이름과 백업 위치를 알린다. 원본

### 복구 범위와 metadata 재시도 보강

사전 `plan.json`은 모든 출력 후보를 기록하지만 자동 복구 권한이 아니다. 완료 시 저장하는
복구 기록 protocol 2의 `run.json`만 자동 복구 범위를 허용한다. 성공 적용은 실제 쓴 파일을, 보상 미완료는
미해결 시도 파일만 기록한다. CAS 409로 거부된 파일은 이후 복구에서도 제외한다. 기록 저장 응답이
유실되면 동일 본문을 재확인하며, 기록이 없거나 구버전이면 전체 계획으로 fallback하지 않는다.
백업 바이트와 UI의 실행/경로 안내는 유지하고 자동 복구를 중단한다.

undo는 경로별 immutable intent/done 기록과 previousRevision을 확인한다. 바이트 복구 뒤 manifest
읽기/저장이 실패하면, 다음 재시도는 원본 바이트와 진행 기록을 검증하고 metadata만 복구한다.
done 뒤 다시 바뀐 파일은 이전 출력과 같은 바이트여도 다시 쓰지 않는다. undo와 commit/보상은
같은 탭의 직렬화 queue를 공유하며, 재컴파일 후 이전 undo는 새 run의 running/tickets/lastRun을
덮지 않는다. 보상은 가능한 원래 lease를 유지하고, 잃었으면 새 lease로 fence한다. undo도 새
mutation lease를 사용한다. 모든 generated PUT/DELETE·manifest PUT은 fence되며
undo 중 세대 전환은 해당 lease를 즉시 폐기한다.

### 최종 확정 지점과 동일 바이트의 다른 요청

출력 PUT과 manifest 시도가 끝난 뒤 취소/세대를 확인한 지점이 commit point다. 그 전 취소는
중단/보상한다. 그 뒤 `run.json` 저장은 복구 범위 기록 마무리이며, 이 대기 중 Stop은 이미 확정된
티켓을 pending으로 되돌리지 않고 후속 웨이브만 막는다. 재컴파일한 새 티켓은 수정하지 않는다.
복구 handle/경고는 직렬화 queue를 넘기기 전에 등록하여 재컴파일 중에도 유지하며, 나중 B의
handle을 늦은 A가 덮지 않는다. UI는 이미 확정된 적용임을 안내한다. 이후 수동 변경은 undo CAS로 보호한다.

새 lease는 현재 mutation을 보호할 뿐 같은 바이트의 역사적 소유권을 증명하지 않는다. 보상은
가능하면 기존 유효 lease를 유지한다. 재획득한 lease를 포함하여 모든 보상/undo는 현재 manifest의
requestId·ticketId·contentHash를 확인한다. 보상은 정확히 이전 manifest entry가 유지된 경우도
허용하지만, 다른 요청 B로 수용 기록이 갱신됐으면 같은 바이트여도 복구하지 않는다. 정상 적용 undo는
해당 요청의 수용 기록을 요구한다. metadata-only 재시도는 durable intent와 previousRevision 및
이전 entry를 함께 확인한다. 손상/읽기 실패/확인 불가는 자동 복구를 거부하고 백업과 handle을 유지한다.
`run.json.phase`는 committed/recovery를 구분하며 이 필드가 없는 이전 범위 기록도 자동 복구하지 않는다.

검증: `manual-change-guard.test.ts`의 최종 run.json afterWrite barrier(Stop·재컴파일·새 B·수동 수정),
동일 바이트 B provenance 및 손상 기록 회귀. `scripts/browser/recovery-provenance.mjs`는 실제 HTTP와
Chromium 두 탭으로 A PUT 반영/응답 유실 → A lease 만료 → B 동일 바이트 수용 → A 보상·undo 거부와
정상 A 뒤 동일 바이트 B 재수용 → 이전 A undo 거부를 실측한다. #281 안정 ID 구현은 포함하지 않는다.

**#367에서 이 결정은 수정됐다.** 같은 파일명을 지우고 다시 쓰면 manifest 파일명 연결만으로 옛 프로젝트를 새 프로젝트로 오인할 수 있다는 재현이 확인됐다. `ProjectSpec.projectId`를 선택 필드로 추가하고, 편집기 문서 ID와 manifest 프로젝트 키로 사용한다. 앱 안 이름 변경과 일반 편집은 ID를 보존하고 Save As 복사본은 새 ID를 발급한다. 새 ID가 같은 파일명으로 들어오면 기존 프로젝트의 `fileName` 연결을 해제하되 기존 파일·수용 기록은 보존하고 새 출력 폴더를 배정한다. Export는 새 ID와 맞지 않는 옛 출력을 새 프로젝트의 현재 출력으로 보지 않는다. 이 구현은 `docs/06-schema-freeze.md`의 별도 PR·팀 승인 조건을 따른다.

### 이름 변경·복사·저장하지 않은 문서

| 일 | 결과 | 근거 |
|---|---|---|
| 앱 안 프로젝트 이름 변경 | 기록의 `fileName`만 새 이름으로 — **같은 ID·같은 폴더**. Export는 그대로 현재, 재생성은 `owned`(묻지 않고 백업 후 교체). 기록하지 못하면 이름 변경은 그대로 두고 이유와 복구 경로를 홈 화면에 알린다(아래 "이름 변경 기록 실패") | `renameProject` → `recordProjectRename` |
| 다른 이름으로 저장(복사) | 새 파일 이름이라 기록이 없다 → 처음 전달할 때 **새 ID·새 폴더**. 원본 프로젝트의 파일·기록은 건드리지 않는다. 진행 중이던 요청은 복사본으로 이어 가지 않는다(아래 "요청 중 다른 이름으로 저장") | `ensureGenerationTarget` |
| 앱 밖에서 이름 변경·복사 | 앱이 알 수 없다 → 새 프로젝트. 옛 폴더의 출력은 남고, Export는 새 자리를 "아직 없음"으로 본다 | 같음 |
| 페이지 이름 변경 | `PageId`가 같아 자리도 같다. 페이지 파일 이름만 바뀐다(아래 컴포넌트 이름 변경과 같다) | — |
| 페이지 복제 | 새 `PageId` → 새 자리 | — |
| 컴포넌트(노드) 이름 변경 | 파일 이름이 바뀌지만 신원(노드 ID)은 같다. Export가 새 이름 티켓을 `renamed`(이전 이름 파일만 있음)로, 옛 파일을 "이름이 바뀐 컴포넌트의 이전 파일"로 보인다. 재생성 뒤에도 옛 파일은 지우지 않는다 | `classifyOutputFreshness` `superseded` |
| 저장하지 않은 문서 | 이 탭의 문서 ID에 세션 프로젝트(`fileName: null`, 폴더 `unsaved…`)를 정해 두고, 처음 저장한 뒤 전달하면 그 파일 이름을 이어받는다. 새로고침하면 세션 연결은 잊는다(그 뒤 전달은 새 프로젝트) | `findGenerationProject` |

**실제 공용 위젯만 공유한다.** 지금 공유되는 것은 한 페이지 안의 반복 형제(같은 구조 → 한 컴포넌트,
`compileTickets` 그대로)뿐이다. 다른 페이지·프로젝트의 같은 이름 컴포넌트는 자리가 달라 공유되지 않고,
같은 페이지의 같은 이름·다른 구조는 기존처럼 `Card`·`Card2`로 갈린다. 페이지를 넘는 공용 위젯은 #265의
widget(PageId) 신원이 생긴 뒤의 일이다(아래 "#265 S0와의 정합").

### 수용 기록 형식 v2

```json
{
  "protocol": 2,
  "projects": {
    "3f6c…": { "fileName": "shop.json", "outputDir": "shop", "createdAt": "2026-10-10T00:00:00.000Z" }
  },
  "entries": {
    "shop/page1/components/Header.tsx": {
      "requestId": "…",
      "ticketId": "Header",
      "componentName": "Header",
      "projectId": "3f6c…",
      "pageId": "page1",
      "componentKey": "component:header",
      "inputScope": "component",
      "inputFingerprint": "sha256:…",
      "contentHash": "sha256:…",
      "ticketProtocol": 3,
      "acceptedAt": "2026-10-10T00:00:00.000Z"
    }
  }
}
```

- 키는 여전히 `generated/` 기준 경로다. 자리가 경로에 들어가므로 경로가 곧 주인 범위다.
- protocol 1(#284·#282 시절) 기록은 2로 올려 읽는다. 그 항목은 **주인 모름**(`projectId: null`,
  `componentKey: null`, `inputScope: "page"`)이다 — `projectKey`(파일 이름)는 주인으로 믿지 않는다. 그래서
  옛 기록은 "현재"나 "마지막 생성 그대로"가 되지 못한다. #282 되돌리기 기록(`run.json`)의 `previousEntry`도
  같은 규칙으로 읽는다.
- 이 앱보다 새 manifest protocol이면 읽기만 하고 **쓰지 않는다**(전달·확정·이름 변경 기록 모두). 빈 기록으로
  읽고 다시 쓰면 새 앱이 남긴 신원을 지우기 때문이다. 요청 중에 새 형식이 된 경우는 아래 "요청 중 새 형식 기록".
- 프로젝트를 새로 기록하거나 파일 이름을 바꿔 쓸 때는 티켓 요청 잠금을 잠깐 잡고, 잠금 안에서 기록을 다시
  읽어 합친 뒤 그 주인으로 쓴다(#284·#282의 manifest 쓰기 소유권과 같은 규칙). 다른 탭이 잠금을 쥐고
  있으면 기다리지 않고 멈춘다. 이미 기록된 프로젝트의 전달은 읽기만 한다.

### PageId 대소문자 충돌

PageId 스키마 패턴(`^[A-Za-z0-9_-]+$`)은 대소문자를 가린다 — `Login`과 `login`은 다른 페이지다. 그런데 생성
자리는 PageId를 폴더 이름으로 그대로 쓰고, Windows·macOS 기본 파일 시스템은 대소문자를 가리지 않아 두 자리가
**한 폴더**다. 수용 기록 키(`shop/Login/…`·`shop/login/…`)는 서로 달라, 한 페이지의 출력을 다른 페이지가 "기록
없음"으로 보고 확인 뒤 덮어쓸 수 있다(조용히 덮지는 않지만 자리를 나눈다는 약속이 깨진다).

| 안 | 장점 | 단점 | 결정 |
|---|---|---|---|
| (a) 같은 프로젝트에 대소문자만 다른 PageId가 있으면 그 페이지들의 생성 전달을 거부하고 이유를 안내 | 폴더 이름 = PageId 규칙이 그대로라 스킬·실측 안내·to-react 직접 실행이 사람이 읽을 수 있는 한 규칙을 계속 쓴다. 앱이 만드는 PageId(`generateNodeId("page", …)`)는 소문자라 앱 안 작업은 막히지 않는다 | 손이나 에이전트가 쓴 JSON의 충돌 쌍은 한쪽 PageId를 바꿔야 생성할 수 있다 | **채택** |
| (b) 폴더 이름 인코딩(소문자화 + 원래 ID의 짧은 해시) | 충돌 쌍도 생성된다 | 모든 자리 이름이 바뀌어(`login-3f6c1a`) 읽기 어렵고, to-react 직접 실행·docs/25 실측 안내가 에이전트에게 해시 계산을 요구한다. 드문 입력을 위해 모든 경로를 바꾼다 | 채택 안 함 |

- 판정은 순수 함수 `pageIdCaseConflicts`(`export/generationIdentity.ts`)이고, `ensureGenerationTarget`이 기록을
  읽기 **전에** 거부한다 — 수용 기록·요청 파일·`generated/` 어디에도 쓰지 않는다. 안내는 다시 눌러도 같은
  이유로 실패하므로 "재시도" 표시를 하지 않는다. 충돌이 없는 다른 페이지는 같은 프로젝트에서도 그대로 전달된다.
- 플랫폼과 상관없이 같은 규칙이다. 대소문자를 가리는 Linux에서도 거부한다 — 같은 작업공간을 Windows·macOS에서
  열면 깨지기 때문이다.
- to-react 직접 실행도 같은 규칙을 따른다(`skills/visual-spec-to-react/SKILL.md` 4번).
- **호환:** 폴더 이름 규칙(PageId 그대로)은 바꾸지 않았다. PageId 자리는 이 PR 전에 배포되지 않았으므로 기존
  작업공간에 남은 자리는 없고, 이 브랜치로 이미 만든 자리도 그대로 이어진다. 충돌 쌍을 가진 프로젝트는 두
  페이지 모두 전달이 막히며, 한쪽 PageId를 바꾸면 그 페이지는 새 자리에서 시작한다(옛 폴더는 건드리지 않는다).

### 요청 중 새 형식 기록

전달 시작 때(`ensureGenerationTarget`) 새 manifest protocol을 거부해도, 요청이 진행되는 사이 다른 writer(더 새
앱)가 기록을 새 형식으로 바꿀 수 있다. 처음 구현은 확정 계획에서 새 형식을 빈 기록으로 읽고 `generated/`를 쓴
뒤 기록 단계에서야 거부해, 기록 없는 출력(Export "확인 불가")이 남았다.

| 시점 | 처리 |
|---|---|
| 계획(`planTicketOutputs`) | 새 형식이면 판정하지 않고 웨이브 전체를 실패로 돌린다. 백업·`plan.json`·`generated/` 모두 쓰지 않는다 |
| 첫 쓰기 직전(확정 순서 2-1, 재비교 뒤) | 다시 읽어 새 형식이면 중단한다. 이 시점까지 쓴 것은 백업과 `plan.json`(복구 허용 기록 아님)뿐이다 |
| 쓰기 뒤 기록(`recordAcceptance`) | 새 형식이면 기록하지 않고, 이번 출력을 확정하지 않은 채 **기존 보상 경로(`compensate`)** 로 넘긴다 |

- 재확인 두 번으로 창은 "첫 쓰기 직전 읽기 ~ 기록 읽기" 사이로 줄었다. 그 창 안에서 바뀌면 출력은 이미 썼다.
- 이때 "확인 불가"로 확정해 두지 않고 보상 경로를 쓰는 이유: 기록을 남길 수 없는 출력은 이 앱이 수용한 결과가
  아니다. 확정으로 두면 티켓이 완료로 보이고 다음 웨이브가 그 출력 위에 이어진다. 보상 경로는 티켓을 실패로
  돌리고, 복구 기록(`run.json`, `phase: "recovery"`)과 "복구 확인 필요" 안내를 남겨 사람이 볼 수 있게 한다.
- 단 보상은 #282 규칙대로 **기록으로 이 요청의 출력임을 증명할 때만** 파일을 되돌린다(`recoveryProvenance`).
  새 형식 기록은 해석할 수 없으므로 증명이 안 되고, 결과적으로 파일은 그대로 두고 "복구 확인 필요"로 남는다.
  같은 바이트를 다른 writer가 썼을 가능성을 배제하지 못한 채 지우는 것보다 남기고 알리는 쪽이 안전하다.
  새 형식 기록 자체는 어느 경우에도 고쳐 쓰지 않는다.

### 티켓 요청 규약 v3

처음 구현은 `generatedRoot`를 더하면서 번호를 v2로 두었다("요청 경로를 그대로 따르면 된다"). 그런데 이미 설치된
v2 스킬은 `filePath`가 **정확히** `pages/<이름>.tsx`·`components/<이름>.tsx`여야 한다고 검증한다. 설치된 스킬
사본은 저장소 스킬을 고쳐도 `visual-spec skills`를 다시 실행하기 전까지 바뀌지 않으므로, 새 GUI + 구 스킬
조합에서는 v2 핸드셰이크가 이 불일치를 잡지 못하고 모든 티켓이 경로 오류로 실패하거나(조용한 실패), 에이전트가
경로 규칙을 임의로 풀 수 있었다(#281 리뷰).

| 조합 | 동작 |
|---|---|
| 새 GUI(v3) + 새 스킬 | v3 요청을 처리하고 `protocol: 3`으로 응답한다 |
| 새 GUI(v3) + 설치된 v2 스킬 | 스킬이 자기 규칙("`protocol`이 2가 아니면 파일을 쓰지 말고 GUI와 스킬 버전을 맞추라고 보고")대로 **쓰기 전에 멈추고** 에이전트 대화에 버전 불일치를 알린다. GUI에서는 만료로 보이고, 만료 안내와 전달 지시문이 `visual-spec skills`로 스킬을 갱신하라고 함께 말한다 |
| 새 GUI(v3) + v2 응답(구 스킬이 그래도 응답을 쓴 경우) | 응답과 출력을 받지 않고 "에이전트의 티켓 응답 스킬이 구버전입니다 … `visual-spec skills`로 갱신한 뒤 다시 전달"을 보인다. 티켓은 대기로 돌아간다 |
| 구 GUI(v2) + 새 스킬 | 스킬이 v2 요청(`generatedRoot` 없음)을 v2 경로 규칙으로 처리하고 `protocol: 2`로 응답한다 |
| 더 새 응답(v4…) | "이 GUI보다 새 규약 — 앱을 업데이트"를 보인다 |

- 기능 협상(요청에 지원 기능 목록을 싣는 안)은 고르지 않았다. 구 스킬이 모르는 필드는 협상할 수 없고, 버전
  번호 하나로 "쓰기 전에 멈춤"이 이미 보장된다.
- 수용 기록 항목의 `ticketProtocol`은 그 출력을 만든 규약 번호다. 이 PR 전 v2로 확정한 출력은 2로 남는다.
- 검증: `test/ticket-protocol-compat.test.ts`가 설치된 v2 스킬의 두 규칙(버전 관문·경로 형식)을 흉내 낸
  fixture 에이전트로 새 GUI의 실제 실행기를 돌린다 — 실제 모델 실행은 아니다.

### 요청 중 다른 이름으로 저장

다른 이름으로 저장(복사)은 `documentStore.fileName`만 바꾸고 문서 ID·스펙·티켓 세대를 그대로 둔다. 처음 구현의
실행기는 요청을 시작할 때의 생성 자리를 들고 세대·취소만 다시 봤으므로, 응답이 늦게 오면 원본 프로젝트의
출력이 확정되면서 **복사본의 티켓이 완료로** 표시됐고, 자동으로 이어지는 다음 웨이브는 새 파일 이름으로 자리를
다시 정해 **복사본의 폴더**로 갔다 — 한 생성이 두 프로젝트에 갈라진다(#281 리뷰).

- `documentStore.projectIdentity`: 이름 있는 파일에서 다른 이름으로 바뀌면 올라간다. 앱 안 이름 변경
  (`adoptRenamedFileName`)과 저장하지 않은 문서의 첫 저장은 같은 프로젝트라 올리지 않는다.
- 티켓 계획은 컴파일 때의 신원(`sourceProjectIdentity`)을 들고, 신원이 바뀌면 계획이 낡은 것으로 본다 — 패널이
  "다른 이름으로 저장해 프로젝트가 바뀌었습니다 … 티켓을 다시 생성해 전달하세요"를 보이고 전달을 막는다.
- 실행기는 생성 자리를 정한 뒤·응답을 받은 뒤·계획 뒤·쓰기 전 확인 뒤·확정 중(`isCurrent`)·확정 뒤에 신원을
  다시 본다. 확정 시점 전에 바뀌었으면 **어느 프로젝트에도 확정하지 않는다**(출력은 `staging/`에 남는다 — 취소와
  같은 수용 경계). 확정 시점이 지난 뒤면 출력은 요청한 원본 프로젝트의 자리·기록에 들어갔고 그 소유권은 맞다.
  어느 경우든 복사본의 티켓은 대기로 돌리고 다음 웨이브를 보내지 않는다.
- 회귀: `generation-ownership.test.ts` "요청 중 다른 이름으로 저장" — A 요청 → B로 저장 → 늦은 A 응답 → 후속
  웨이브 시도에서 `generated/`·티켓·기록이 각각 맞는지, 확정 중 저장, 그리고 B에서 다시 생성하면 B의 새 자리에
  처음부터 만들어지는지 본다. 앱 안 이름 변경은 요청 중이어도 같은 자리에 확정된다.

### 이름 변경 기록 실패

`recordProjectRename`이 기록하지 못하는 경우 — 다른 탭(또는 이 탭)의 티켓 요청이 잠금을 쥐고 있음, 기록을 읽거나
쓰지 못함, 새 형식 기록 — 처음 구현은 그 오류를 버리고 성공만 알렸다. 기록이 옛 이름을 들고 있으면 다음 전달은
새 프로젝트(새 폴더)로 시작해 이 프로젝트의 출력과 끊긴다.

- 이름 변경 자체는 이미 끝났으므로 뒤집지 않는다. 결과에 `warning`을 담아 홈 화면이 이유와 복구 경로를 보인다.
- **복구 경로:** 이 탭이 "기록 대기"(현재 이름 → 최초 출발 이름)를 들고 있다가, Export와 다음 전달에서 옛 이름의 기록을
  이 프로젝트로 이어받고, 다음 전달 때 잠금 안에서 기록을 다시 쓴다. 연속 변경(A→B→C)도 최초 출발 이름을 직접 보존한다.
  새로고침하면 대기를 잊는다 — 그 전에 전달하지 않았다면 보통 새 프로젝트로 시작한다.
  낡은 대상 파일명 기록이 남은 경우는 아래 "재검증 정정"과 "#281 남은 한계"의 파일명 재사용 경계다.
- 회귀: `generation-ownership.test.ts` "이름 변경 기록 실패"(잠금 사용 중·기록 읽기 실패 → 안내, 다음 전달에서
  같은 자리·기록 복구), `rename-project.test.ts`(warning 전달·신원 세대 유지).

### 재검증 정정: 구조 손상과 미기록 rename의 대상 충돌

- 유효 JSON과 protocol 번호만으로 읽기 성공으로 보지 않는다. Export와 생성 위치 결정은 `entries` 객체와
  각 항목, protocol 2의 `projects` 객체와 각 프로젝트 항목을 확인한다. 누락·null·배열·잘못된 항목이면
  검사/전달을 중단하고 기록을 덮지 않는다. 관대한 `parseGenerationManifest`는 구형 항목·복구 읽기에 남기되,
  위치 결정 전에 `isReadableGenerationManifest`로 구분한다. protocol 1은 `projects`가 없는 원래 형식을 유지한다.
- 확정 404 및 정상 registry에서 미등록인 direct-to-react 출력의 후보 폴더는 계속 읽는다. 다른 등록 프로젝트가
  소유한 폴더는 후보로 쓰지 않는다. 구조가 손상된 기록을 빈 registry로 바꿔 추측하는 경로와 다르다.
- 앱 안 A→B 이름 변경을 잠금 때문에 기록하지 못했으면, 이 탭이 알고 있는 출발 이름 A가 과거 B의 filename
  기록보다 우선한다. Export·ZIP은 A를 읽고, 다음 전달은 잠금 안에서 A의 ID·폴더를 B로 잇고 낡은 대상 이름을
  비운다. A→B→C 연속 변경도 A에서 출발한다. B·C의 기존 생성 파일은 삭제하거나 이동하지 않는다.
- **이름 재방문 정정:** 직전 이름을 잇던 대기 목록은 A→B→C→B에서 B↔C 순환이 되어 A를 잃었다.
  현재 이름 하나가 최초 출발 이름을 직접 가리키도록 바꾸고, 떠난 이름의 대기 항목은 지운다. 중간 이름
  재방문·원래 이름 복귀 후 다시 이동·원래 이름 복귀, 잠금 중 복구 실패 후 재시도에도 A를 유지한다.
  기록 복구 후에는 대기 항목을 제거해 중간 이름을 쓰는 별도 문서가 A를 이어받지 않는다.
- `test/export-identity.test.ts`의 실제 HTTP 회귀는 구조 손상 10종, 404/v1/v2 미등록 출력, 등록 폴더 배제,
  잠금 중 rename·연속 rename·잠금 해제 뒤 연속 rename을 검증한다. ZIP 생성 바이트도 비교한다.
  `scripts/browser/generation-ownership.mjs`는 실제 Home rename UI·작업공간 서버·ZIP 바이트로 두 재현과 정상
  fallback과 A→B→C→B→A→B→C 이름 재방문·복구 재시도를 대조한다. `run-journeys.sh`의 여섯 번째 필수
  여정이며 외부 모델을 호출하지 않는다.
- 새로고침/다른 탭에서는 pending rename을 모른다는 기존 한계는 남는다. 그 경우 보통 새 폴더로 시작하지만,
  과거 기록이 같은 destination 파일명을 들고 있으면 아래의 **외부 파일명 재사용 한계**가 적용될 수 있다.
  이번 수정은 같은 탭이 알고 있는 rename 신원을 잃지 않게 하며 영속 rename journal을 도입하지 않는다.

### Windows 장치 이름

`con`·`prn`·`aux`·`nul`·`com0`~`com9`·`lpt0`~`lpt9`(Microsoft 문서의 예약 이름, 위 첨자 `¹²³` 포함)는 대소문자와
상관없고 확장자가 붙어도(`Con.tsx`·`nul.txt`) Windows가 장치로 해석한다. PageId 스키마 패턴은 이 값을 허용한다.
Node 작업공간 서버는 `\\?\` 경로로 그런 폴더·파일을 실제로 만들어 버릴 수 있지만, 그 뒤 탐색기·git·편집기·
PowerShell 같은 일반 Win32 프로그램은 그 경로를 열거나 지우지 못한다.

| 대상 | 처리 |
|---|---|
| PageId(생성 자리 폴더) | 생성 전달 전에 이유를 밝혀 거부한다(재시도 표시 없음). 대소문자 충돌과 같은 "거부" 방식이다 — 몰래 다른 이름으로 바꾸면 스킬·Export·기록의 경로 규칙이 갈라진다 |
| 티켓 이름(파일 `<이름>.tsx`) | 같다. 화면·레이어 이름을 바꾼 뒤 티켓을 다시 생성하라고 안내한다 |
| 프로젝트 폴더 | 파일 이름에서 후보를 만들 때 `-project`를 붙인다(이미 있던 규칙, 판정을 `isWindowsDeviceName`으로 통일). 프로젝트 파일 이름 자체는 `projectFileName`이 이미 거부한다 |

- 플랫폼과 상관없이 같은 규칙이다. 생성 결과는 다른 기기로 옮겨진다.
- 회귀: `test/generation-device-name.test.ts`(임시 폴더 + 실제 작업공간 서버). 거부 시 기록·`generated/`에 아무것도
  쓰지 않는 것을 보고, Windows에서는 거부하지 않았을 때 서버가 만든 `con` 폴더가 일반 Win32 경로로는 보이지 않는
  것까지 실제 파일로 확인한다.

### Export 검사 불가와 다운로드 직전 확인

처음 구현의 Export는 기록을 관대한 reader로 읽어 **읽기 실패도 "기록 없음"(빈 기록)** 으로 판정했다. 빈 기록이면
다른 등록 프로젝트가 쓰는 폴더를 모른 채 파일 이름에서 자리를 추측하게 되고, 이름 변경 뒤나 같은 slug의 `-2`
폴더가 있을 때 **다른 프로젝트의 파일**을 골라 ZIP으로 내려받을 수 있었다. 또 결과 캐시는 편집기 변경만 구독해,
다른 이름으로 저장한 뒤에도 원본 프로젝트의 결과가 남아 내려받을 수 있었다(#281 리뷰).

| 기록 상태 | Export |
|---|---|
| 읽음(protocol 1·2) | 기록된 프로젝트의 자리. 기록에 없는 프로젝트면 파일 이름 후보 폴더 — 다른 등록 프로젝트가 쓰는 폴더면 쓰지 않는다 |
| 확정된 404(기록 없음) | 파일 이름 후보 폴더(직접 실행한 to-react 출력). "확인 불가(기록 없음)"로 표시하고 ZIP은 허용한다 |
| 읽기 실패(HTTP 오류·네트워크) | **검사 불가** — 파일을 고르지 않고 ZIP을 만들지 않는다. 작업공간 연결을 확인하고 다시 검사하라고 안내 |
| 이 앱보다 새 형식 | 검사 불가 — 앱 업데이트 안내 |
| 손상(JSON 아님·모르는 모양) | 검사 불가 — 기록을 고치거나 다시 전달하라고 안내 |

- 리뷰의 "신원이 확인되지 않은 임의 root 금지"는 **읽기 실패 상태의 추측 root 금지 + 다른 등록 프로젝트가 쓰는
  폴더 금지**로 해석했다. 기록이 확인된 상태(읽음·확정 404)에서 이 파일의 기록이 없을 때 후보 폴더를 보는 것은
  GUI 전달 없이 to-react를 직접 실행한 사용자의 Export를 위해 남긴다(판정은 "확인 불가"라 "현재"가 되지 않는다).
- 캐시 무효화: Export 결과는 파일 이름·프로젝트 신원이 바뀌면 지운다(`useDocumentStore` 구독).
- 다운로드 직전 확인: `isExportTargetCurrent`가 검사한 문서·페이지·스펙·파일 이름과 지금 상태를 비교한다. 자산을
  읽기 전과 ZIP을 내려받기 직전 두 번 보고, 다르면 내려받지 않는다.
- 회귀: `generation-ownership.test.ts` "Export 검사 불가"(404·500·네트워크·새 형식·손상, 이름 변경·같은 slug)와
  `export-identity.test.ts`(A Export → B로 저장 → 재검사 전 다운로드에서 A 바이트가 나오지 않음).

### Export 생성 세대 판정(#281로 넓힘)

| 티켓 판정 | 조건 | 전체 판정에서 |
|---|---|---|
| `current` | 이 프로젝트·페이지·컴포넌트의 기록, 해시·입력 지문 일치 | 현재 |
| `stale` | 이 프로젝트·페이지의 기록·해시는 맞지만 지문이 다르거나, 같은 자리의 다른 컴포넌트(같은 이름의 다른 노드) 출력 | 오래됨 |
| `renamed` | 이 자리에 파일은 없지만 같은 신원의 이전 이름 출력이 있다 | 오래됨 |
| `changed` | 기록과 바이트가 다르다 | 확인 불가 |
| `foreign` | 바이트는 기록과 같지만 다른 프로젝트·페이지의 기록이거나 주인 모름 | 확인 불가 |
| `unrecorded` | 기록 없음 | 확인 불가 |
| `missing` | 파일 없음 | 아직 없음 |

티켓 파일이 아닌 자리 안 파일(ZIP에 함께 담김)도 전체 판정에 넣는다(#353의 보강 그대로) — 기록 없음·바뀜·
남의 기록이면 확인 불가, 이 프로젝트·페이지의 이전 출력(이름을 바꾼 옛 파일·지금 없는 컴포넌트의 파일)은
오래됨이다. 그래서 이름 변경 뒤 재생성까지 끝나도 옛 파일이 남아 있으면 전체는 "부분"이고, 사람이 그
파일을 지우면 "현재"가 된다. 앱은 지우지 않는다 — 사람이 고쳤을 수 있고, 마지막 웨이브 전에는 다른 파일이
아직 옛 이름을 import할 수 있다. 패널은 그 파일 목록과 "확정 뒤 수정됨" 여부를 보인다.

컴포넌트 지문 덕분에 "일부만 B"가 갈린다. 예: Header의 제목 문구·색을 A→B로 바꾸면 Header·페이지 티켓은
`stale`이고 Card·Content는 `current`라 전체는 **부분**이다(파일·참조 검사는 4/4·오류 0 그대로). Header만
다시 만들면 Header가 `current`, 페이지가 `stale` — 여전히 부분이다. 페이지 티켓의 지문은 페이지 전체라
페이지 어디가 바뀌어도 전체가 "현재"가 되지 않는다.

### #265 S0와의 정합

`docs/24-screen-relations-design.md`(#265 S0-1, 승인 대기)의 결정과 어긋나지 않게 신원·경로만 정했다.

- D9 "프로젝트 widget PageId로만 공유, 이름 기반 합치기 없음": 이 PR도 이름으로 공유하지 않는다. 생성 자리가
  PageId 단위라 widget이 생기면 `generated/<프로젝트 폴더>/<widget PageId>/`가 그 위젯의 자리가 된다.
  인스턴스를 가진 페이지가 위젯을 import하는 경로(자리 밖 상대 경로)와 ZIP 범위는 S1-8/9에서 정한다.
- D11 "프로젝트 단위 Ticket 형태와 다음 티켓 요청 규약 버전은 #281 신원·경로 합의 뒤": 이 PR은 Ticket 형태
  (docs/11)를 바꾸지 않았다. 티켓 요청 규약은 `generatedRoot` 추가 때문에 v3으로 올렸다(위 "티켓 요청 규약 v3") —
  프로젝트 단위 요청은 그 다음 버전(v3 다음)의 일이다. 컴포넌트 신원은
  `(PageId, 종류, 대표 NodeId)`라 그 다음 Ticket 형태의 "티켓별 sourcePageId + 로컬 instances"와 그대로 맞는다.
  프로젝트 ID는 IR 밖에 있으므로 다음 Ticket 형태가 필드로 들고 다닐 필요가 없다. 번호는 docs/24가 정하지 않고
  비워 둔다 — "v0.2"·"protocol 2·3"은 이미 쓰이는 번호(Ticket 요청 규약 v2·v3, manifest·`run.json` protocol 2)와 겹친다.
  (2026-10-13 추가) 이후 리더 결정으로 번호가 정해졌다 — Ticket 스키마([11](11-ticket-schema-freeze.md)) v0.2와 티켓 요청 규약 v4이며,
  manifest·`run.json`의 `protocol`은 바꾸지 않는다(위 ["티켓 요청 규약 v4 예정"](#티켓-요청-규약-v4-예정--265-d11)).
- 이동 그래프와 생성 의존 DAG: 컴포넌트 지문은 `dependsOn`(생성 DAG)만 본다. navigate·openModal 같은 이동
  관계는 아직 IR에 없고, 들어와도 생성 의존으로 옮기지 않는다는 S0 결정과 충돌하지 않는다.
- 저장 ID와 런타임 DOM ID 구분: 신원에 쓰는 것은 저장 ID(PageId·NodeId)뿐이다.

### 남은 한계 (#281)

- **앱 밖에서 이름을 바꾸거나 복사한 프로젝트는 새 프로젝트로 본다.** 옛 출력은 옛 폴더에 남고 새 자리는
  처음부터 만든다. 남의 출력을 덮는 쪽으로는 틀리지 않는다.
- **낡은 기록이 같은 파일 이름을 들고 있으면** 그 이름으로 새로 만든 프로젝트가 옛 ID·폴더를 이어받는다(앱
  밖에서 파일을 지우고 같은 이름으로 다시 만든 경우). 그때도 바이트가 기록과 같은 파일만 `owned`이고 바꾸기
  전에 백업한다. 앱 안 이름 변경은 대상 이름을 들고 있던 낡은 기록의 이름을 비워 이 경우를 줄인다.
- 프로젝트 기록은 읽고-합치고-쓰기다. 새 프로젝트 기록·이름 변경 기록은 잠금 안에서 쓰지만, 외부 writer와의
  CAS는 없다. **티켓 요청이 잠금을 쥔 동안에는 이름 변경을 기록하지 못한다** — 이름 변경 자체는 끝나고, 홈
  화면이 이유와 복구 경로를 보인다. 이 탭에서 다음에 전달하면 기록을 다시 쓰지만, 그 전에 새로고침하거나 다른
  탭에서 전달하면 새 폴더로 시작한다(위 "이름 변경 기록 실패").
- 세션 프로젝트(저장하지 않은 문서)는 새로고침하면 연결을 잊는다. 남은 `unsaved…` 폴더는 주인 없는 출력이다.
- 프로젝트 폴더 이름은 처음 정한 파일 이름에서 나온다. 이름을 바꿔도 폴더는 그대로라 폴더 이름과 프로젝트
  이름이 달라질 수 있다(안정성을 읽기 쉬움보다 앞에 뒀다).
- 컴포넌트 지문은 하위 트리 밖을 보지 않는다(판정 범위의 선택). 에이전트가 컴포넌트 밖의 값을 컴포넌트
  코드에 옮긴 경우 그 컴포넌트는 "현재"로 남을 수 있지만, 페이지 티켓이 페이지 전체 지문이라 전체는 "현재"가
  되지 않는다. 자산 파일(`assets/`) 바이트 변경은 지문에 들어가지 않는다(#284와 같다).
- 이름이 바뀐 컴포넌트의 옛 파일은 지우지 않는다. 옛 파일의 수동 변경은 새 이름 파일로 옮겨지지 않는다 —
  패널이 "확정 뒤 수정됨"으로 알릴 뿐이다.
- to-react 직접 실행의 폴더 규칙(대소문자 PageId 충돌 거부 포함)은 에이전트가 지키는 약속이다. 기록은 여전히
  GUI만 쓴다.
- Windows 장치 이름인 PageId·티켓 이름은 생성할 수 없다(전달 전 거부, 위 "Windows 장치 이름"). 앱이 만드는
  PageId는 `page…`라 해당 없고, 손이나 에이전트가 쓴 JSON·레이어 이름에서만 생긴다.
- 요청 중 다른 이름으로 저장하면 그 요청의 출력은 어느 프로젝트에도 확정하지 않고 `staging/`에 남긴다. 앱은
  그 출력을 복사본으로 옮겨 주지 않는다 — 복사본에서 티켓을 다시 생성해 전달해야 한다.
- 요청 중 새 manifest protocol은 첫 쓰기 직전까지 두 번 확인한다. 그 뒤 기록 직전에 바뀐 경우 쓴 파일은 출처를
  증명할 수 없어 되돌리지 않고 "복구 확인 필요"로 남는다(위 "요청 중 새 형식 기록").

### 버전과 요청 필드 제안

기존 `buildTicketRequest`·`parseTicketResponse`와 v3 동작은 유지한다. 프로젝트 producer/parser는
별도 함수와 `PROJECT_TICKET_PROTOCOL_VERSION = 4`를 사용한다. 따라서 기존 상수를 일괄 4로
바꿔 단일 화면 요청을 조용히 새 형태로 전환하지 않는다. 배포 스킬은 protocol별 분기 후 각각의
요청/응답 형식을 지킨다. v4 요청을 구 v3 스킬이 받으면 쓰기 전에 거부한다.

프로젝트 v4 요청의 아래 필드는 필수이며, 이 목록 밖 필드와 null은 허용하지 않는 안이다.

| 필드 | 형태 / 의미 |
|---|---|
| protocol | 상수 4 |
| id | 새 요청마다 생성하는 `[A-Za-z0-9_-]{1,128}` 문자열. snapshot/staging 경로 segment로 검증 |
| project | 요청 시점 불변 ProjectSpec 전체. projectId 필수, 프로젝트 검증 통과 |
| projectRoot | `generated/` 기준 기존 projectId 소유 outputDir. 페이지별 generatedRoot와 구별 |
| plan | docs/11의 ProjectPlan 전체. ticket/route/entry/artifact/제외 범위의 정본 |
| tickets | 이번 wave의 항목 배열. 아래 필드만 가진다 |
| responsePath | 현행 `runtime/ticket-response.json` |
| outputRoot | 현행 `staging/<id>` |
| assets | 아래 정규 자산 mapping 목록. 자산이 없으면 빈 배열 |
| inputSnapshotPath | `runtime/project-input-<id>.json` (작업공간 기준) |
| inputSnapshotSha256 | 해당 불변 snapshot 파일 UTF-8 바이트의 SHA-256 |

wave 항목은 `id`, `sourcePageId`, `componentName`, `kind`, `instances`, `filePath`, `outputPath`를
필수로 가진다. 앞 다섯 값은 plan.tickets의 해당 항목과 정확히 일치한다.
`filePath = <projectRoot>/<sourcePageId>/pages|components/<componentName>.tsx`,
`outputPath = <outputRoot>/<filePath>`이며 기존 Windows 이름/대소문자 충돌/루트 탈출 검사도 적용한다.
`page`/`pageId`/페이지별 `generatedRoot`는 v4 최상위에 받지 않는다. project와 충돌하는 두 번째
화면 snapshot을 두지 않는다. wave가 비어 있으면 요청을 쓰지 않는다. plan.artifacts는 GUI 소유이므로 wave/results에
포함하지 않으며 에이전트가 그 파일을 쓰면 범위 밖 출력으로 거부한다. project.projectId와
plan.projectId는 같아야 하고 routes/entry/제외 목록을 요청에서 재해석하지 않는다.

### 응답·수용 제안

응답은 기존 키를 유지한 `{ protocol: 4, requestId, results }`이며 각 결과는
`{ ticketId, status: "done" | "failed", message? }`다. failed의 message는 비어 있지 않은 문자열을
요구한다. 추가 속성과 null은 거부한다. requestId 불일치는 기존처럼 stale이고 현재 요청의
실패로 덮어쓰지 않는다. id가 일치하면 protocol→형태→중복/누락/미요청 ticketId를 검사한다.
results의 ID 집합은 wave와 정확히 같아야 한다. done만으로 성공 확정하지 않고 파일/소유권/
지문/현재 요청 세대/수동 변경 보호를 검사한다. failed 결과를 다른 티켓 성공으로 상쇄하지 않는다.

오류 분류 후보는 `version-mismatch`, `malformed`, `duplicate-ticket`, `missing-ticket`,
`unexpected-ticket`, `invalid-source`, `invalid-dependency`, `invalid-output-path`, `stale-input`이다.
실제 parser 반환 타입과 GUI 안내의 연결은 스키마/규약 PR에서 단위 테스트로 확정한다.

### 불변 입력 snapshot과 자산 mapping

assets 항목은 `{ sourcePath, sha256, byteLength, mediaType, zipPath }`이며 모두 필수다.
sourcePath는 승인된 workspace assets 경계 안의 프로젝트가 실제 참조한 정규 상대 경로다.
S1에서 제외한 widget만 참조하는 자산은 생성/ZIP mapping에서 제외하되 전체 IR 검증은 유지한다.
실제 경로/symlink 경계 확인 후 바이트를 읽고 SHA-256(64자리 소문자 hex)과 byteLength를 계산한다.
파일 확장자를 신뢰하지 않고 지원 이미지 타입을 판별한다. 동일 바이트는 동일 mediaType과
정규 확장자를 사용한다: PNG .png, JPEG .jpg, GIF .gif, WebP .webp, AVIF .avif, BMP .bmp,
ICO .ico, SVG .svg. 지원 타입 판별 실패/모순은 요청 전 오류이며 기존 SVG/외부 참조 정책을 완화하지 않는다.
`a.jpg`와 `b.jpeg`의 바이트가 같으면 두 sourcePath가 하나의 `assets/<sha256>.jpg`로 대응한다.
같은 파일명이라도 바이트가 다르면 별개다. 같은 hash인데 실제 바이트가 다르면 충돌 오류로 거부한다.

GUI는 요청을 쓰기 **전에** `runtime/project-input-<id>.json`을 create-only로 저장한다. 이 위치는
기존 runtime .json allow-list 안이며 staging/generated에 이미지 파일을 쓰도록 권한을 넓히지 않는다.
기존 파일이 있으면 정확히 같은 바이트인지 확인하고 다르면 요청을 중단한다. 재시도는 새 requestId다.
이 snapshot은 `{ protocol: 1, requestId, projectId, project, plan, assets }`이고 assets 각 항목은
위 mapping에 `dataBase64`를 추가한다. base64를 디코딩한 길이/hash/type을 모두 대조한다.
UTF-8 JSON 직렬화는 객체 key를 사전순 정렬하고 배열 순서는 보존하며 공백 없이 쓴다.
그 파일 바이트의 hash가 요청 inputSnapshotSha256다. request의 project/plan/assets(mapping만)는
snapshot과 정확히 같아야 한다. agent는 이 **읽기 전용 snapshot의 바이트만** 읽으며 mutable
sourcePath를 다시 열지 않는다. 손상/누락/hash 불일치 시 코드 쓰기 전에 거부한다.
요청 중 임의 수정도 hash 검사로 탐지한다. “불변”은 외부 writer가 물리적으로 수정 불가능하다는 주장이 아니다.

### 모듈 인식 URL 재작성과 ZIP

agent는 로컬 자산을 `vsb-asset:<sha256>` token으로만 표현한다. img src의 정적 문자열과
정적 style/background-image의 url() 위치를 지원한다. agent가 임의의 로컬 asset import나
동적 URL 조합을 만들거나 mapping에 없는 token/URL을 쓰면 거부한다. 이 제한은 **agent 입력**에
대한 것이며 아래 GUI가 만드는 검증된 모듈 자산 참조까지 금지하는 뜻이 아니다.

브라우저의 `<img src="../../assets/…">`와 inline style의 url()은 TSX 파일 위치가 아니라
`document.baseURI`에 상대적이다. 따라서 이전 초안의 **TSX-source-relative 문자열 치환은 폐기**한다.
GUI는 AST에서 token을 찾아 충돌 없는 지역 바인딩을 생성하고 다음처럼 정적 모듈 참조로 바꾼다.
예시의 hash는 실제 mapping 값으로 치환하며, `new URL`의 첫 인자는 리터럴이어야 한다.

```tsx
// login/pages/LoginPage.tsx — GUI가 추가한 binding
const vsbAsset0 = new URL("../../assets/<sha256>.png", import.meta.url).href;
// img src token → src={vsbAsset0}
// inline background token → style={{ backgroundImage: `url("${vsbAsset0}")` }}
```

JSX 속성/inline style에는 위 바인딩의 **빌드가 해석한 URL 값**을 사용한다. token을 일반 텍스트에
전역 replace하거나 `new URL(variable, import.meta.url)`로 바꾸지 않는다. 매핑을 공유하는 같은
모듈의 참조는 바인딩 하나를 재사용한다. `runtime/Host.tsx`의 첫 인자라면 `../assets/<hash>.png`다.
출력 code 검사/hash/확정은 변환 후 수행한다. 원본 IR sourcePath는 바꾸지 않는다.
실제 CSS 모듈의 정적 url()은 CSS 파일 기준 상대 경로로 변환하고 번들러의 CSS module graph에서
처리해야 한다. 미처리 public CSS로 복사하거나 TSX 문자열과 혼동하지 않는다. plan에 선언되지 않은
CSS 출력은 여전히 거부하며 이 규칙이 임의의 추가 CSS 산출물 권한을 주지 않는다.

ZIP의 **소스 트리**는 기존처럼 `<PageId>/pages|components/…`, `runtime/…`, `assets/<hash>.<ext>`다.
GUI가 각 source 모듈에서 자산 파일까지의 POSIX 상대 경로를 계산하고 ZIP의 실제 바이트와 대조한다.
자산 바이트는 생성 과정의 generated/staging에 쓰지 않고, Export 때 수용 sidecar의 snapshot에서
ZIP assets/에 한 번만 넣는다. 코드와 자산은 같은 projectId/plan 소유이며 바인딩은 해당 출력의
소유권을 따른다. 번들러가 나중에 만든 dist chunk/이미지는 build 산출물이지 새 Agent Ticket이 아니다.

독립 앱은 ZIP 소스를 **asset-aware ES module bundler**로 빌드해야 한다. 첫 검증 기준은 Vite의
정적 `new URL(literal, import.meta.url)` 변환이며, 테스트 앱은 `base: "./"`로 빌드하여 같은 dist를
root와 nested prefix에 배포한다. 소비 앱이 명시 base를 쓰면 실제 배포 prefix와 일치시켜 다시
빌드/검증한다. 첫 계약은 client-side ESM 빌드이며 SSR의 서버 file URL 해석까지 보장하지 않는다.
테스트 mount는 trailing slash가 있는 entry URL이고 별도 SPA router/base 설정은 소비 앱에서 검증한다.
`.tsx`를 그대로 복사하거나 asset 변환 없는 tsc 출력만으로 배포 성공이라 하지 않는다.
ZIP은 이 소스 배치/빌드 요구를 export 안내에 담고 소비 앱의 package/router 설정을 덮어쓰지 않는다.
preview도 snapshot 자산을 제공하는 같은 module-aware 빌드/VFS가 필요하다. 존재하지 않는
workspace generated/assets 파일이나 source-relative 브라우저 문자열로 preview 성공을 가장하지 않는다.

URL 정책 세대는 `assets-2`이며 templateVersion의 `project-runtime-1/assets-2`와 입력 지문에
포함한다. 이전 source-relative 문자열 결과를 같은 지문의 current로 재사용하지 않는다.
Export 직전 현재 sourcePath 바이트를 snapshot과 다시 비교하고 변경/누락이면 stale로 막는다.
그 후 이미 검증한 보유 바이트로 ZIP을 만들어 다시 읽는 TOCTOU를 피한다. 외부 URL은 로컬
바이트 보장 밖이며 네트워크 의존성을 기록한다.

### 빌드 후 자산 수용 검사와 분리 fixture 근거

- asset 없는 경로/미등록 token/잘못된 base가 통과하지 않는 음성 사례. 허용되지 않은 CSS 파일도 거부.

2×3 PNG(73 bytes, SHA-256 `949ff4d564a25629663895b0b6e070342836121696a0165d32e6e9e16f8f6e29`),
`login/pages/LoginPage.tsx`의 정적 new URL, img/inline background와 imported CSS를 사용했다.
TypeScript noEmit 검사, Vite 8.2.1 production build(`base:"./"`, `assetsInlineLimit:0`),

emitted PNG를 HTTP 200으로 읽고 2×3으로 decode했다. 이는 **선택한 빌드 메커니즘의 fixture 증거**이며

이전 `../../assets/<source-hash>.png` 브라우저 문자열은 root/nested 모두 decode 실패함도 확인했다.

### 프로젝트 provenance와 기존 parser 호환

현재 manifest protocol 2와 backups/<runId>/run.json protocol 2의 **형태와 버전을 그대로 유지**한다.
`normalizeEntry`가 미지 필드를 보존하지 않고 복구 parser가 필드/범위를 검사하므로, 새 provenance를
그 객체에 덧붙여 저장하지 않는다. 새 GUI 전용 별도 파일을 사용한다:

- 현재 수용 기록: `runtime/project-generation-<sha256(projectId UTF-8)>.json`.
- 복구 보조 기록: `backups/<runId>/project-recovery.json`.
- 직전 sidecar 원문 백업: `backups/<runId>/project-generation.json` (직전 기록이 있을 때만).

수용 sidecar의 필수 필드는 `{ protocol: 1, projectId, projectRoot, plan, templateVersion,
inputFingerprint, assets, outputs, committedRunId }`다. assets에는 mapping과 dataBase64를 모두
보존하여 임시 입력 snapshot GC 뒤에도 확정 시점 바이트를 검증할 수 있다. outputs는
`{ id, scope: "page" | "project", sourcePageId?, filePath, sha256, requestId, inputFingerprint }[]`다. scope=page는
sourcePageId 필수, scope=project는 금지한다. 모든 경로는 같은 projectRoot 안의 plan 허용 목록과
정확히 일치한다. SHA-256은 **재작성 후** 출력 바이트다. templateVersion의 첫 값은
`project-runtime-1/assets-2`로 호스트 템플릿과 URL 정책 세대를 함께 식별한다. 추가 필드와 미지 protocol은 거부한다.
중간 wave의 outputs는 일부일 수 있으나 plan의 모든 ticket/artifact ID가 정확히 한 번 존재하고
각 출력의 inputFingerprint·바이트·자산 검사가 통과해야만 프로젝트 current다. 재사용 출력도 해당
범위의 지문을 다시 대조하며 기록에 없는 지문을 채워 넣지 않는다. 부족한 집합은 partial로 표시하고
프로젝트 ZIP을 막는다. 부분 성공 기록을 프로젝트 전체 완료 기록으로 표시하지 않는다.

화면 티켓의 기존 manifest entry는 현행 필수 필드와 ticketProtocol=4로 기록한다. 가짜 PageId가
필요한 프로젝트 산출물은 그 entry에 넣지 않고 sidecar에만 소유권을 기록한다. 새 프로젝트
검증은 sidecar의 화면 출처/requestId와 기존 manifest의 동일 항목도 대조한다. 구 v3 writer가
출력을 바꾸거나 기록을 지우면 새 GUI가 프로젝트 current로 승격하지 않는다. 구 GUI는 프로젝트
생성/ZIP 기능을 제공하지 않으며, sidecar를 읽는 척하거나 프로젝트 산출물을 page 소유로 자동 덮어쓰지 않는다.

확정은 기존 workspace 잠금 아래서 overwrite 검토→원본 백업→출력 검증/쓰기→기존 manifest 기록→
sidecar 마지막 기록/재읽기 순서다. sidecar 교체는 읽은 revision에 대한 CAS로 하며
충돌하면 덮어쓰지 않고 복구 확인 상태로 남긴다. 복구 보조 기록은 `{ protocol: 1, runId, sidecarPath,
previousSidecarPath, previousSha256, writtenSha256 }`이며 직전 없음은 두 previous 필드의 null로만 표현한다.
파일 복구 범위는 기존 run.json의 path/ticketId/previousRevision/backupPath/writtenRevision/
previousEntry 형태로 기록한다. 프로젝트 artifact의 ticketId는 plan artifact ID, previousEntry는
기존 manifest 항목이 없으면 null이다. 기존 run parser를 통과하도록 실제 parser 회귀를 필수로 둔다.
sidecar 복구는 새 GUI가 보조 기록과 현재 hash를 대조한 경우에만 직전 원문을 복원/제거한다.

sidecar 쓰기 실패·중간 crash·두 기록 불일치·구 GUI의 파일만 복구는 **unverified/복구 확인 필요**다.
이전 성공 기록을 새 출력에 맞춰 추측하지 않는다. 기존 parser가 sidecar를 몰라도 run.json/manifest는
계속 읽을 수 있지만, 그것만으로 v4 자산/프로젝트 provenance가 증명되지는 않는다. 오래된 기록에
충분한 sidecar가 없으면 파일을 보존하고 unverified로 표시하여 프로젝트 Export/자동 덮어쓰기를 막는다.
이 unverified 규칙은 v4 프로젝트 판정에 적용하며 기존 v3 단일 화면의 판정을 소급 변경하지 않는다.
수동 변경 보호와 요청 세대/Save As 검사를 없애지 않으며, 취소된 요청의 snapshot은 완료 기록이 아니다.

### 지문·예시·수용 조건

전체 프로젝트 완료 지문은 projectId, pageOrder, 생성 대상 page/modal snapshot, plan,
템플릿/URL 재작성 규약 버전, 정규 자산 mapping+바이트 hash를 포함한다. 개별 화면의 지문은
그 화면과 도달 modal/포함 widget의 cycle-safe closure를 ID 순으로 정렬하여 계산한다.
S1에서는 widget instance가 없지만 S2 closure 계약을 제거하지 않는다. navigate 대상의 본문만
바뀌면 출발 화면을 무조건 stale로 만들지 않되 registry/프로젝트 계획은 재평가한다.
모든 입력에 무효 관계가 있으면 생성/Export를 거부하며 widget을 검사에서 건너뛰지 않는다.

서로 다른 원래 확장자가 같은 JPEG 바이트를 가리키는 mapping 형태 예시(아래 hash/길이는
설명용 자리값이며 실제 요청 fixture는 실제 바이트에서 계산해야 한다):

```json
[
  { "sourcePath": "assets/a.jpg", "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa", "byteLength": 123, "mediaType": "image/jpeg", "zipPath": "assets/aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa.jpg" },
  { "sourcePath": "assets/b.jpeg", "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa", "byteLength": 123, "mediaType": "image/jpeg", "zipPath": "assets/aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa.jpg" }
]
```

별도 스키마/구현 PR의 필수 검증:
1. v3→새 스킬은 v3 응답, v4→실제 구 v3 스킬은 쓰기 전 거부, v4 GUI의 v3 응답 거부.
2. plan metadata 소실 없는 round-trip, entry/route 대응, 프로젝트 소유 산출물의 허용 경로/실패 시 ZIP 차단.
3. modal A↔B 이동과 생성 DAG 비순환, widget의 명시 제외와 전체 검증 오류 차단.
4. snapshot 생성 후 source 변경에도 agent 입력은 고정; 수용/Export에서 stale 거부. snapshot 변조/hash 불일치 거부.
5. jpg/jpeg 동일 바이트 공유, 다른 바이트 분리, 모듈 인식 재작성, ZIP 소스 build 후 root/nested 실제 이미지 로드.
6. 기존 strict manifest/run parser로 구 기록 및 새 page/artifact 복구 기록 판독; sidecar 없음/손상/미지 버전,
   partial commit/구 GUI 복구/수동 변경은 unverified이며 원문을 버리지 않음.

이 초안은 여섯 기술 선택을 구체화한 리뷰 대상이며 승인 완료나 구현 완료가 아니다. 현재 런타임은
변경하지 않는다. 선행 계약·별도 schema 정상 수용 뒤 compiler/GUI/스킬/Export를 구현하며,
실제 에이전트→ZIP→독립 앱 확인 전에는 #265 완료가 아니다.

### 프로젝트 runtime 기록의 저장 관문 (S1-9 선행 구현)

`runtime/project-input-<requestId>.json`과 `runtime/project-generation-<sha256(projectId)>.json`에만
기존 revision 헤더를 적용한다. GET/성공 PUT은 실제 바이트 SHA-256을 반환한다. 두 경로의 PUT은
기대 revision이 필수(누락 428, 잘못된 형식/정규 경로 400)다. 일반 runtime v3 파일의 동작은 유지한다.

- snapshot은 `missing`만 받으며 기존 파일은 동일 바이트라도 409다. producer는 409 뒤 별도 GET으로
  정확한 바이트를 확인해야 하고, 다른 바이트이면 중단해야 한다. 완료된 임시 파일을 hard link로
  create-only 게시하여 CAS 확인 이후 외부 프로세스가 만든 파일도 덮어쓰지 않는다. hard link를
  지원하지 않는 파일 시스템에서는 500으로 중단하며 overwrite rename으로 fallback하지 않는다.
- provenance는 `missing` 또는 읽은 SHA-256으로 비교/쓰기한다. 앱 내부 동시 쓰기는 기존 공통
  mutation queue로 직렬화하고 stale 쓰기는 409다. HTTP 밖 writer와의 완전한 파일 시스템 잠금은
  아니다. 수용/복구는 여전히 요청 잠금·hash 재확인·sidecar-last 순서를 지켜야 한다.
- 대소문자만 다른 snapshot 파일명은 별개 파일로 만들지 않는다. reserved prefix의 비정규
  경로도 거부한다. allow-list·origin·symlink 경계와 runtime DELETE 금지는 바꾸지 않는다.

이 단계는 byte 저장 경계만 구현한다. snapshot 내용/자산 검증, producer, sidecar 복구 및 생성/Export
연결은 후속이며 이 API 통과를 프로젝트 생성 완료로 세지 않는다.

### 불변 입력 bytes 준비/검증 (S1-9 pure API)

`buildProjectInputSnapshot(requestId, project, plan, assets)`는 문맥 검증 뒤 정규 JSON content,
`runtime/project-input-<id>.json` path, **접두사 없는 64자리 SHA-256**을 반환한다. 파일 쓰기/요청
전송은 하지 않는다. `parseProjectInputSnapshot(content, expectedHash, requestId)`는 hash만 믿지
않고 exact key/version/신원/전체 plan 문맥 및 자산 base64·길이·hash·type·zipPath를 다시 검사한다.
반환된 문자열은 원본 프로젝트의 이후 편집과 독립이다. producer는 이 문자열을 #394의
create-only 저장 관문으로 먼저 확정해야 한다. v3 builder/parser는 바꾸지 않는다.

`projectAssetPaths`는 검증된 page/modal의 모든 image와 base/responsive image background를
수집한다(숨김 포함). widget-only 경로는 S1 mapping에서 제외한다. mapping은 실제 참조 집합과
정확히 같아야 하며 중복/누락/추가 sourcePath를 거부한다. assets 목록은 sourcePath 순서로 만든다.
workspace reader와 같은 decoded segment 규칙으로 중첩 assets 경로도 수집하며 실제 파일 읽기는 기존 canonical/symlink 경계를
통과한 reader 책임이다. data URI는 project JSON 안의 그대로인 바이트 표현으로 보존하고 https/http
참조는 네트워크 의존으로 남긴다(이 pure API가 외부 fetch를 하지는 않는다). blob·미해결 assetId·
public 절대 경로·탈출 상대 경로는 standalone 보존을 보장할 수 없으므로 명시 오류다.

`createProjectAssetSnapshot`은 파일명 대신 byte signature로 PNG/JPEG/GIF/WebP/AVIF/BMP/ICO/SVG
타입과 정규 확장자를 고른다. 예를 들어 PNG 바이트의 .jpg source도 .png ZIP으로 대응한다.
ICO의 정규 mediaType은 image/x-icon이다. 이 판별은 전체 이미지 decoder나 SVG sanitizer가 아니다.
SVG는 UTF-8 XML 선언/주석 뒤 svg root를 판별하며 DTD/별도 namespace prefix 등 판별되지 않는
형식은 오류다. 기존 assets 읽기/외부 참조 정책을 확장하지 않는다. ZIP의 실제 decode와 production
module-aware URL 수용 검사는 후속이다. 동일 JPEG 바이트의 jpg/jpeg는 동일 hash.jpg로 대응한다.

이 전달은 저장된 snapshot/자산 재검증까지의 pure 경계다. HTTP 수집/dispatch, v4 wire validator,
코드 AST URL 변환, sidecar 수용/복구와 GUI/Export 연결은 아직 별도 작업이다.

#395 검증 보강: 금지 문자·끝 공백/점·빈 segment는 서버와 공유하는 predicate로 거부한다.
sourcePath는 이미 decoded된 IR 경로이며 reader URL은 각 segment를 인코딩한다. parser도
sourcePath 오름차순을 강제하므로 배열을 뒤집어 hash를 다시 계산해도 거부한다.

완성된 snapshot의 **UTF-8 JSON 전체 바이트**는 workspace PUT과 공유하는 32 MiB 상한 이하여야
한다. 개별 base64 및 자산 합계는 먼저 검사하고, project/plan/metadata/JSON escaping까지 포함한
최종 길이도 검사한다. parser 역시 hash 계산 전에 같은 한도를 검사한다. 초과 시 원본을 변경하거나
자산을 버리지 않고 명시 오류로 중단한다. 저장 한도를 늘리거나 자동 축소하지 않는다.

### 프로젝트 v4 pure wire 경계

`PROJECT_TICKET_PROTOCOL_VERSION = 4`와 `buildProjectTicketRequest`/`validateProjectTicketRequest`/
`parseProjectTicketResponse`를 별도로 추가한다. 기존 상수/함수/단일 화면 v3는 그대로다. builder는
검증한 snapshot 문자열/hash/requestId와 **소유권 기록에서 가져온 projectRoot**, wave ticketIds를
받는다. snapshot을 다시 검증하고 정확한 plan 티켓만 wave에 싣는다. 빈/중복 wave, GUI artifact,
미완료 선행 dependency, Windows 장치명/탈출/대소문자 생성 경로·PageId 충돌은 거부한다.
각 sourcePageId·instances·출력 경로는 plan에서 계산하며 외부 값을 신뢰해 덮어쓰지 않는다.

request validator는 원본 snapshot 문자열과 기대 projectRoot를 따로 받아 완성된 요청을 재구성하고
전체를 대조한다. 추가/누락/null/undefined 필드를 허용하지 않는다. 반환은 valid/request 또는
valid:false/code/message다. code는 version-mismatch, malformed, duplicate-ticket, missing-ticket,
unexpected-ticket, invalid-source, invalid-dependency, invalid-output-path, stale-input이다.
내용 hash/요청 신원 검증 실패는 stale-input, sourcePageId 불일치는 invalid-source, 소유 폴더와
파생 경로 불일치는 invalid-output-path, 나머지 필드 불일치는 malformed로 구분한다.

response parser는 stale requestId를 먼저 무시한다. 현재 ID라면 protocol 4와 exact result shape,
중복/미요청/누락 ID를 검사한다. failed는 trim 뒤 비지 않은 message가 필수다. 응답은
kind:stale, kind:malformed/code/message, 또는 kind:results/results다. done은 파일 수용 성공을
뜻하지 않고 후속 출력 검증으로 넘길 후보일 뿐이다. v3/v4 혼합 fallback은 없다.

이 함수들은 소유권 레지스트리를 만들거나 status=done의 provenance를 인증하지 않는다. producer는
기대 projectRoot와 상태를 기존 소유권/수용 기록으로 확정한 뒤 불변 snapshot을 create-only 저장하고
잠금 안에서 dispatch해야 한다. 이 전달은 pure wire이며 기존 GUI/runner/스킬/Export를 아직 전환하지 않는다.

#398 경계 보강: requestId는 staging 디렉터리이므로 CON/NUL/COM1 등 Windows 장치명을
거부한다(snapshot 파일명에 접두사가 붙는 것만으로 staging 경로가 안전해지지는 않는다).
`serializeProjectTicketRequest`는 compact JSON 전체의 UTF-8 크기를 공유 32 MiB PUT 상한과
대조한다. builder도 반환 전에 이를 호출한다. producer는 이 직렬화 결과를 보내며 pretty-print를
한다면 그 결과의 크기를 다시 검사해야 한다. snapshot이 들어가도 wave metadata가 더해진 request는
초과할 수 있다. v4 응답보다 새 버전이면 GUI 업데이트, 오래된 응답이면 스킬 갱신을 안내한다.

### 불변 입력의 workspace 저장 준비

`prepareStoredProjectRequest`는 await 이전에 문서/plan/wave/출력 폴더를 복사하고 전체 plan 문맥을
검증한다. 기존 strict workspace reader로 자산을 수집하여 snapshot을 만들고 v4 wave를 검증한 뒤,
`expectedRevision=missing`으로 snapshot만 쓴다. 성공 또는 409 충돌 뒤에는 저장 파일을 다시 읽어
정확한 UTF-8 문자열과 hash를 대조해야 요청 객체를 반환한다. 409라도 바이트가 다르면 덮어쓰지
않고 중단한다. 다른 전송 실패는 기존 파일이 있더라도 성공으로 바꾸지 않는다.

모든 I/O 전후에 문서 세대/취소를 확인한다. 저장 중 취소되면 미사용 immutable snapshot이 남을 수
있지만 요청을 반환하거나 request 파일을 쓰지는 않는다. runtime DELETE 제한을 우회해 지우지 않는다.
이 함수는 소유권 폴더/수용 상태를 발급하거나 잠금을 대신하지 않는다. 호출자는 manifest에서 검증한
projectRoot와 provenance로 확인한 티켓 상태를 전달하고, 반환 뒤 실제 dispatch 전에 현재 세대와
request 잠금을 재확인해야 한다. 수용/Export에서는 현재 소스 자산과 snapshot을 다시 대조한다.
아직 기존 GUI/스킬 dispatch를 v4로 전환한 것은 아니다.
