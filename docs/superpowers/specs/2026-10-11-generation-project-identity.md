# Generation project identity for #367

Status: implementation on `codex/367-project-recreated-identity`; schema review and approval are required before merge.

## Problem

`runtime/generation-manifest.json` currently resolves a project by its spec filename. If a user deletes `shop.json` and creates a different project at the same path, `findProjectByFileName` returns the old project ID and output directory. The new project can then inherit the old generated files and their ownership records.

Filename and content are not stable identity. Content can legitimately change, and a recreated project can have identical content. Filesystem modification time is also unsuitable by itself: normal saves replace the spec file atomically, and copied files can retain timestamps. Treating either as identity would either lose project continuity on ordinary saves or still misidentify a recreated project.

## Proposed contract

Add an optional, persisted `projectId` to `ProjectSpec`. It is an opaque UUID assigned by the GUI, stable across edits and in-app rename, and regenerated by Save As/copy. The generation manifest stores the same ID beside its project record. Ticket generation may reuse a manifest project only when the loaded spec's `projectId` matches it.

When the ID is absent, the editor assigns an ID in memory. Saving persists it; if generation happens first, the manifest registers the new ID in a fresh, unoccupied output directory. It never adopts a same-filename manifest record. Legacy manifest entries remain readable but do not gain ownership of a document that has no matching ID.

## Lifecycle cases

- Edit and save: preserve the ID.
- Rename through the app: preserve the ID and output directory.
- Save As/copy: generate a new ID and output directory.
- Delete and recreate at the same filename: the new document receives a new ID and cannot adopt old outputs.
- Legacy spec without an ID: treat prior same-name output as unowned/needs confirmation; never silently overwrite it or report it as current.
- Legacy VisualSpec input: Open migrates it to ProjectSpec in memory and assigns an ID; Home rename writes the ProjectSpec form and that ID to disk. Reopening the renamed file in a new browser context retains the same ID.

## Compatibility and scope

This changes the frozen Visual Spec IR schema. Existing project documents without `projectId` must remain readable, but the schema's `additionalProperties: false`, type generation, save path, examples, migration, and validation fixtures must be updated together. Generated output records and Export classification must continue to mark legacy output as foreign or requiring confirmation until the project identity is established.

Keep the generation manifest protocol change, if any, separate from the Visual Spec schema decision. Do not infer identity from `name`, filename, output directory, content hash, or filesystem timestamps.
