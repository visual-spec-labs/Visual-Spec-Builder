# 홈 화면 — 자연어 초안 경로 설계 (#286)

기준: 2026-10-05 제품 점검 `D01` · P1 · develop `ad3b6f17d183b69b1589707e7e8d032806ba4c88`.

## 문제

`HomeScreen.tsx`의 첫 실행(상태 2, 빈 목록) 화면은 세 갈래 선택지를 보이지만,
**"자연어로 초안 만들기"와 "빈 캔버스에서 시작"이 완전히 같은 동작이다**
(`handleNewScreen` 하나를 공유한다, `04-gui-spec.md` §2 현재 상태 표도 이미
이렇게 적어 뒀다). 자연어를 고른 사람도 결국 빈 캔버스로 떨어지고, 실제 자연어
입력은 에디터에 들어간 뒤 `NaturalLanguageBar`를 따로 찾아야 한다.

또한 두 경로 어디에도 **"GUI는 에이전트를 직접 실행하지 않는다"**(#219, A안)는
사실이 드러나지 않는다 — 자연어를 선택한 사람은 그 문장을 입력하면 바로 뭔가가
자동으로 만들어질 것으로 기대하기 쉽지만, 실제로는 별도 터미널에서 사람이 직접
켠 에이전트가 응답을 써야 진행된다.

## 범위

**이번 작업은 "처음 시작"(상태 2, 목록이 빈 경우)만 다룬다.** 상태 1(목록이 있을
때)의 헤더 `+ 새 화면` 버튼은 바꾸지 않는다 — 이슈 본문이 "처음 시작의 직접
편집/자연어 초안 경로"로 범위를 좁혔고, 반복 사용 중의 "+ 새 화면"은 이미
목적이 분명한 단축 버튼이라 같은 두 갈래를 다시 물을 이유가 적다. "기존 화면
불러오기" 타일도 바꾸지 않는다 — 문제가 있던 쪽은 자연어/캔버스 둘뿐이다.

## 결정 (사용자 확인, 2026-10-07)

두 가지 흐름 중 아래를 골랐다.

1. **"자연어로 초안 만들기"는 에디터로 바로 들어가지 않고, 홈 화면 안에서 먼저
   작성한다.** 입력창·초안 예시·수동 에이전트 안내를 모두 홈 화면의 인라인
   패널에서 보여주고, 작성을 마친 뒤에만 에디터로 넘어간다. (근거: 완료
   조건이 "자연어 선택 → 입력 포커스 → 초안 예시 → 수동 에이전트 안내"를
   선택의 결과로 요구한다 — 에디터로 먼저 넘어가면 이 순서를 홈 화면이 아니라
   에디터 쪽에서 다시 조립해야 한다.)
2. **"초안 만들기"를 눌러도 에이전트 요청을 즉시 보내지 않는다.** 작성한 문구를
   에디터의 자연어 입력창에 그대로 채워 넣고 포커스만 준다 — 실제 전송("요청"
   버튼)은 사용자가 에이전트를 켜 둔 뒤 직접 누른다. (근거: 에이전트가 아직
   안 켜져 있으면 즉시 전송은 3분 뒤 timeout으로 끝난다 — #283이 이미 확립한
   "수동 전달" 원칙과 같은 이유다.)

## 설계

### 상태 흐름

```
상태 2(빈 목록, 세 갈래 선택)
  │
  ├─ "빈 캔버스에서 시작"       → 그대로: newSpec() + openEditor() (변경 없음)
  ├─ "기존 화면 불러오기"       → 그대로: openSpec() (변경 없음)
  └─ "자연어로 초안 만들기"     → 상태 2-nl(인라인 작성 패널)
                                   │
                                   ├─ "뒤로"       → 상태 2로 복귀, 입력 버림
                                   └─ "초안 만들기" → newSpec() + 문구를 홈 draft
                                                      스토어에 적재 + openEditor()
                                                      → NaturalLanguageBar가 마운트
                                                        시 그 문구를 읽어 입력칸에
                                                        채우고 포커스한다
```

```
┌──────────────────────────────────────────────┐
│           첫 화면을 만들어 봅시다              │
│          어떻게 시작하시겠습니까?              │
│      ┌──────────────────────────┐            │
│      │ 자연어로 초안 만들기        │            │

│      ├──────────────────────────┤            │

│      │ 직접 요소를 배치            │            │

│      │ JSON 파일을 엽니다          │            │
│      └──────────────────────────┘            │

```

### 상태 2-nl — 자연어 초안 작성 (신규)

```
┌──────────────────────────────────────────────┐
│           자연어로 초안 만들기                 │
│        만들고 싶은 화면을 설명해 주세요         │
│                                              │
│  ┌────────────────────────────────────────┐  │
│  │ (포커스) 예: 로그인 화면 — 이메일, 비밀번호 │  │
│  │ 입력창과 로그인 버튼이 있는 화면          │  │
│  └────────────────────────────────────────┘  │
│                                              │
│  예시  [로그인 화면] [대시보드] [설정 화면]      │
│                                              │
│  ⓘ 이 요청은 별도 터미널에서 실행한 Claude      │
│    Code/Codex가 처리합니다. 아직 실행하지       │
│    않았다면 지금 준비해 두세요 — 에디터에서      │
│    준비되면 지시를 복사해 전달할 수 있습니다.    │
│                                              │
│          [ 뒤로 ]     [ 초안 만들기 ]          │
└──────────────────────────────────────────────┘
```

| 요소 | 문구 | 활성 조건 | 포커스 |
|---|---|---|---|
| 입력창 | placeholder "예: 로그인 화면 — 이메일, 비밀번호 입력창과 로그인 버튼이 있는 화면" | 항상 활성 | 패널이 열리는 즉시 자동 포커스 |
| 예시 칩 3개 | "로그인 화면" · "대시보드" · "설정 화면" (각각 아래 "초안 예시" 전문을 채운다) | 항상 활성 | 클릭 시 입력창에 전문을 채우고 입력창에 포커스를 되돌린다(이어서 바로 고쳐 쓸 수 있게) |
| 안내 문구 | "이 요청은 별도 터미널에서 실행한 Claude Code나 Codex가 처리합니다. 아직 실행하지 않았다면 지금 준비해 두세요 — 에디터에서 준비되면 지시를 복사해 전달할 수 있습니다." | — (정적 텍스트) | — |
| 뒤로 | "뒤로" | 항상 활성 | 클릭하면 상태 2로 돌아간다. 입력 중이던 문구는 버린다 |
| 초안 만들기 | "초안 만들기" | 입력칸 trim 결과가 빈 문자열이면 비활성 | 제출(클릭 또는 입력창에서 Enter) 시 에디터로 전환되므로 이 컴포넌트는 그대로 unmount된다 |

초안 예시 전문(클릭 시 입력창에 채워지는 값, `homeDraftExamples.ts`):

1. "로그인 화면 — 이메일, 비밀번호 입력창과 로그인 버튼이 있는 화면"
2. "대시보드 — 상단에 요약 카드 3개, 아래에 표가 있는 화면"
3. "설정 화면 — 좌측에 메뉴 목록, 우측에 토글 스위치 목록이 있는 화면"

예시 1은 기존 `examples/login-screen.json`·`docs/14-getting-started.md`가 이미
쓰는 "로그인 화면" 설명과 결을 맞췄다 — 사용자가 나중에 getting-started 문서를
봐도 같은 종류의 화면을 가리킨다는 걸 알 수 있다.

### 에디터로 넘어간 뒤

`NaturalLanguageBar`가 마운트될 때(= 홈에서 에디터로 들어올 때마다, `App.tsx`가
`screen` 세 갈래 분기로 에디터 서브트리를 통째로 마운트/언마운트하므로 매번
새로 실행된다) 아래를 한 번 확인한다.

1. 새로 만든 `store/homeDraft.ts`에서 보류 중인 문구를 꺼낸다(꺼내면 즉시 비운다 —
   같은 문구가 다음에 에디터를 다시 열 때 또 채워지지 않도록).
2. 있으면 `instruction` state를 그 값으로 설정하고 입력창에 포커스한다.
3. 없으면(홈에서 "빈 캔버스로 시작"으로 들어왔거나, 기존 화면을 열었거나,
   에디터 안에서 그냥 페이지를 오갔을 때) 아무것도 하지 않는다 — 기존 동작
   그대로다.

**자동 전송은 하지 않는다**(위 결정 2) — 입력칸에 문구가 보이고 포커스가 가
있을 뿐, "요청" 버튼은 여전히 비활성 조건(빈 문자열)을 만족하지 않아 활성
상태이지만 누르는 주체는 사용자다.

### 컴포넌트/모듈 계획

- `src/features/editor/store/homeDraft.ts` — 모듈 스코프 변수 하나(`draft:
  string | null`)와 `setHomeDraft(text)`/`consumeHomeDraft(): string | null`
  (읽으면서 비운다) 두 함수뿐인 순수 모듈(자체 code-review 대응으로 zustand
  스토어에서 바꿨다 — 두 호출부 모두 반응형 훅이 아니라 명령형 호출만 쓰므로
  zustand의 구독 장치가 필요 없다, `ticketRunner.ts`의 모듈 스코프
  `activeCancel`과 같은 자리). 홈 화면과 에디터가 서로 다른 마운트 트리라
  React state로는 못 넘기므로(`App.tsx`의 `screen === "home" ?
  <HomeScreen/> : <EditorLayout/>`이 완전히 다른 서브트리다) 모듈 바깥의
  공유 상태가 필요하다.
- `src/features/editor/ui/homeDraftExamples.ts` — 위 세 예시 문자열만 담는
  순수 배열(`HOME_DRAFT_EXAMPLES: { label: string; text: string }[]`). UI와
  분리해 두면 문구만 바꿀 때 JSX를 안 건드려도 되고, 배열 내용 자체를
  테스트로 고정할 수 있다.
- `HomeScreen.tsx` — 상태 2 렌더링에 로컬 state 둘(`draftMode: boolean`,
  `draftText: string`)을 추가한다. 세 번째 타일의 `onClick`을
  `handleNewScreen` 공유에서 `() => setDraftMode(true)`로 바꾸고, `draftMode`
  일 때는 3-타일 목록 대신 위 인라인 패널을 그린다.
- `NaturalLanguageBar.tsx` — 마운트 effect(기존 "언마운트 시 폴링 취소"
  effect와 별개로 하나 더) 하나만 추가한다. 입력 `<input>`에 `ref`를 달아
  포커스 대상으로 쓴다(지금까지는 ref가 없었다).

### 사용성 관찰 방법

완료 조건의 "문서 없이 첫 화면 생성까지의 사용성 관찰을 기록한다"는 사람
대상 사용성 테스트가 아니라, **Chrome 브라우저로 처음 보는 사람 역할을 하며
직접 그 경로를 걸어 보고 막히는 지점을 기록하는 것**으로 한다(이 저장소에
실제 신규 사용자 모집 체계가 없다 — 검증과 변경 절차의 "브라우저 실측"
범주). 아래 "검증" 절에 기록한다.

## 검증

`pnpm run typecheck` · `pnpm run lint` · `pnpm run build` 모두 통과했다.
`pnpm test`는 기존과 동일한 17개 실패(Windows 심링크·권한 등, 무관)/1564개
통과/2개 건너뜀 — 신규 `test/home-draft.test.ts`(3개)·
`test/home-draft-examples.test.ts`(2개)가 더해진 수치다. 둘 다 순수 로직
(`store/homeDraft.ts`의 `setHomeDraft`/`consumeHomeDraft`, 예시 배열의 모양)만
검증한다 —
이 저장소에 React 컴포넌트 렌더 테스트(React Testing Library 등)가 없어
`HomeScreen.tsx`/`NaturalLanguageBar.tsx`의 JSX 배선 자체는 테스트로 고정하지
못했다. 그 부분은 아래 브라우저 실측으로 대신했다.

**브라우저 실측(Chrome, 처음 보는 사람 역할).** 별도 임시 작업공간
(`visual-spec init` 직후, 특정 파일 없음 → 상태 2)에서 `pnpm`으로 띄운 개발
서버를 문서 없이 처음 접근하듯 걸어 봤다.

- ✅ 상태 2(빈 목록)의 세 갈래 선택지가 그대로 보인다.
- ✅ "자연어로 초안 만들기"를 누르면 입력창이 **자동으로 포커스된 채** 인라인
  패널로 바뀐다 — placeholder·예시 칩 3개·수동 에이전트 안내 문구·"뒤로"/
  "초안 만들기"(빈 입력이라 비활성)가 설계한 그대로 보인다.
- ✅ 예시 칩("로그인 화면")을 누르면 입력창에 전문이 채워지고 **포커스가
  입력창으로 되돌아오며**, "초안 만들기"가 활성(주황색)으로 바뀐다.
- ✅ 직접 타이핑도 같은 방식으로 "초안 만들기"를 활성화한다.
- ⚠️ **"초안 만들기" 제출 이후(에디터 진입) 화면은 이번에도 확인하지
  못했다.** 클릭 또는 입력창에서 Enter로 제출하자마자 이 세션의 Chrome
  확장이 `Runtime.evaluate`/`document_idle` 대기에서 45초 이상 멈췄다 —
  `docs/20-manual-agent-handoff-ui.md` "검증" 절이 #283에서 이미 기록한
  것과 같은 증상이다. **이번 변경과 무관하다는 것을 직접 확인했다** — 같은
  세션에서 이 PR이 전혀 건드리지 않은 "빈 캔버스에서 시작" 타일을 눌러도
  똑같이 멈췄다(새 탭에서 재현). 즉 "자연어로 초안 만들기"의 새 제출 경로가
  원인이 아니라, 홈 → 에디터로 넘어가는 전환 자체(두 경로가 공유하는
  `openEditor()`/`EditorLayout` 마운트)가 이 Chrome 확장 세션에서 막히는
  **기존 증상**이다.
- 그래서 "`store/homeDraft.ts`에 적재한 문구가 실제로 `NaturalLanguageBar`의
  입력칸에 나타나고 포커스되는지"는 **코드 추적으로만** 확인했다 —
  `HomeScreen.tsx`의 `handleCreateDraft`가 `setHomeDraft(text)` 뒤
  `openEditor()`를 부르고, `App.tsx`가 그 즉시 `EditorLayout`(과 그 안의
  `NaturalLanguageBar`)을 새로 마운트하며, `NaturalLanguageBar`의 신규
  effect가 마운트 시 정확히 한 번 `consumeHomeDraft()`를 불러 `instruction`을
  설정하고
  `instructionInputRef.current?.focus()`를 부른다. 이 effect의 의존성 배열이
  `[]`이고 `App.tsx`가 홈↔에디터를 완전히 다른 서브트리로 마운트/언마운트하는
  것은 기존 코드(이 PR이 바꾸지 않음)이므로, "에디터에 들어올 때마다 정확히
  한 번 실행된다"는 전제가 깨질 경로가 없다. 다음 세션에서 이 Chrome 확장
  증상이 풀리면 실제 화면으로 다시 확인해야 한다.

`/code-review`를 돌려 두 건을 찾아 고쳤다.

1. **`handleCreateDraft`에 중복 제출 가드가 없었다.** `handleRename`은 이미
   `renaming` 가드로 같은 문제를 막고 있는데, "초안 만들기"는 가드가 없어서
   Enter 두 번을 빠르게 누르거나 Enter·클릭이 겹치면 `newSpec()`(안의
   `settle()` 대기 구간)이 끝나기 전에 `handleCreateDraft`가 다시 들어와
   `newSpec()`+`setHomeDraft()`+`openEditor()`가 두 번 겹쳐 실행될 수 있었다.
   오늘은 두 동작이 멱등이라 눈에 보이는 증상이 없지만, `renaming`과 같은
   자리의 가드가 빠진 것 자체가 결함이었다. `submittingDraft` state를
   추가해 재진입을 막고, "뒤로"·"초안 만들기" 둘 다 제출 중엔 비활성화했다.
2. **`store/homeDraftStore.ts`가 zustand `create()`를 썼지만 아무도 반응형
   훅으로 구독하지 않았다.** 두 호출부(`HomeScreen.tsx`·
   `NaturalLanguageBar.tsx`) 모두 `getState()`류의 명령형 호출만 썼다 —
   `useHomeDraftStore(selector)` 형태의 호출은 저장소 전체에 하나도 없었다.
   리렌더를 구독할 곳이 없으면 zustand가 더하는 구독 장치는 불필요한
   간접 비용이다. `store/homeDraft.ts`로 이름을 바꾸고 zustand 없이 모듈
   스코프 변수 하나 + `setHomeDraft`/`consumeHomeDraft` 두 함수로 다시
   짰다 — `ticketRunner.ts`의 모듈 스코프 `activeCancel`과 같은 자리의
   상태다. 공개 동작(적재·소비 규칙)은 그대로다.
