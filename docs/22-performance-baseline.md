이 문서는 **병목을 입증하고 후속 우선순위를 정하는 기록**이다. 최적화 구현은 여기서 하지 않았다.

## 결론 먼저

| 순위 | 후속 작업 | 근거 |
|---|---|---|

- 값은 위 "비교 — React production 빌드" 표와 같은 수준이다(같은 방식이므로 기대한 대로다).
- 같은 production 모드로 GUI 주요 흐름을 헤드리스 Chrome으로 직접 조작해 확인했다. 홈 진입, 열기, 편집, Undo, Save(디스크 반영), 에이전트 연결 `gui-state.json` 공개, 디스크 변경 감지·불러오기, Export 패널이 모두 동작했고 콘솔 오류·예외는 없었다.
- **방식 선택.** 이슈의 두 갈래 중 (가) 개발 서버를 `NODE_ENV=production`으로 띄우는 쪽을 골랐다. (나) `vite build` 결과를 작업공간 미들웨어가 붙은 서버로 제공하는 쪽은 실행마다 빌드(또는 빌드 캐시 판정)가 필요하고, 지금 개발 서버 전용(`apply: "serve"`)인 미들웨어를 preview 서버에도 붙여야 한다. (가)는 CLI가 넘기는 환경 변수 하나로 같은 효과(위 표)를 낸다. 그래서 사용자는 여전히 개발 서버의 모듈을 받고 production 번들(548kB)은 받지 않는다 — 코드 분할(5)은 낮은 우선순위를 유지한다.
- **개발 모드에서만 있던 것이 사라진다.** React Fast Refresh가 꺼져(plugin-react가 production에서 건너뛴다) GUI를 띄운 채 도구 저장소 소스가 바뀌면(예: `git pull`) 상태 보존 갱신 대신 페이지 전체가 새로 고쳐진다. StrictMode의 effect 이중 실행이 없어지고, React 오류 문구가 `Minified React error #…`로 줄어든다. 셋 다 도구를 고치는 사람에게 필요한 것이라 `pnpm dev`(개발 모드)나 `VISUAL_SPEC_REACT_DEV=1`로 그대로 쓸 수 있다. 앱 코드에는 `import.meta.env`·`NODE_ENV` 분기가 없다.
- **의존성 캐시를 모드별로 나눴다**(`vite.config.ts`의 `cacheDir` — production은 `node_modules/.vite-production`). Vite는 `NODE_ENV`가 바뀌면 사전 번들 캐시를 다시 만들고, 그 직후 첫 화면에서 새 의존성을 찾으면 페이지를 한 번 새로 고친다. CLI(production)와 `pnpm dev`(development)를 오갈 때마다 이 일이 생기지 않게 한다.
- 남은 병목은 후속 2(#315, 홈 미리보기 — S4 홈 1.0초·DOM 17만 개)다. 편집은 노드 1000개에서 "다음 태스크까지 경과"가 23~24ms로 노드 100개보다 커서, 실제 입력 경로로 다시 잰다(#317).

## 후속 2(#315) 적용 뒤

홈 카드 미리보기를 **카드 목록 스크롤 영역의 보이는 부분 근처(위아래 200px)에 들어온 카드만** 그리게 했다(`ui/HomeScreen.tsx`의 `ProjectPreview`·`useSeenOnce`, `IntersectionObserver`의 `root`는 카드 목록의 스크롤 요소). 그 전에는 같은 크기(208×140)의 빈 자리만 두고, 한 번 그린 카드는 스크롤로 벗어나도 지우지 않는다. 그리는 카드는 노드를 **전부** 그린다.

**후보 비교**

| 후보 | 결정 | 이유 |
|---|---|---|
| 보이는 카드만 그리기 | **채택** | 그리는 카드의 모습은 그대로다. 줄어드는 양은 화면 밖 카드 수에 비례한다 |
| 노드 수·깊이 상한 | 버림 | 한 번 구현했다가 셀프 리뷰에서 되돌렸다. 그리는 순서(깊이 우선)로 자르면 세로 배치에서만 위쪽이 남는다. row·grid 배치에서는 첫 형제가 상한을 다 써서 화면에 보이는 영역이 빠진다. 또 잘린 형제가 빠지면 남은 형제의 정렬(center·space-between·hug 높이)이 달라져, 첫 화면 안의 노드도 위치가 바뀐다. 레이아웃을 모르고 자르는 한 카드와 실제 화면의 일치(04 홈 사양·`ProjectCard` 주석)를 지킬 수 없다 |
| 썸네일 이미지 캐시 | 버림 | DOM을 이미지로 굽는 수단(별도 렌더러·라이브러리)이 필요하다. 스펙이 바뀔 때마다(에이전트·디스크 변경 포함) 무효화해야 한다. "스펙 JSON에서 매번 즉석 렌더"(docs/open-questions.md 해결 항목)와도 어긋난다. 위 채택안으로 충분한지 먼저 본다 |

## 후속 3(#316) 적용 뒤

#315 뒤 프로파일(S4 홈, production)에서 파일 파싱·스키마 검증이 홈 CPU의 약 30~40%였다(`parseSpecJson`·JSON 파싱·Ajv `validate*`). 그래서 진행했다. 다만 카드에 보이는 이름·페이지 수·크기가 파일 내용에서 나오므로, 이슈 원안(메타데이터만 먼저 보이고 보이는 카드부터 읽기)은 카드를 빈 껍데기로 보여 주거나 깨진 파일을 늦게 걸러 목록이 출렁인다. 대신 **화면 동작은 그대로 두고 앞에서부터 그린다**(`ui/homeProjects.ts`의 `loadWorkspaceProjectsProgressively`):

- 파일은 한꺼번에 요청하고, 파싱·검증은 카드 순서(최근 수정순)대로 첫 묶음은 창으로 어림한 첫 화면 카드 수(`homeFirstBatch` — 1600×1000에서 42), 그 뒤 50개씩 한다. 묶음 사이에는 **두 프레임**을 양보해 브라우저가 앞 카드와 그 미리보기를 그리게 한다(`setTimeout(0)`만으로는 다음 묶음 파싱이 그리기보다 먼저 돌아 첫 화면이 늦어졌다). 숨긴 탭은 프레임이 오지 않으므로 다음 태스크로 넘어간다.
- 묶음이 끝날 때마다 카드를 뒤에 이어 붙인다. 깨진 파일은 지금처럼 목록에 나오지 않고, 이미 보인 카드의 순서는 바뀌지 않는다. 다 읽을 때까지 "프로젝트 N개 · 불러오는 중…"으로 표시한다.
- 이름 변경으로 목록을 다시 읽으면, 아직 뒤를 읽던 처음 읽기는 멈추고 남은 파일 요청도 취소한다. 다시 읽기가 실패해도 "불러오는 중" 표시는 꺼진다. 한꺼번에 돌려주는 `loadWorkspaceProjects`(이름 변경 뒤 다시 읽기)는 한 묶음으로 끝까지 읽는다.

측정에 **첫 화면**(카드가 모두 들어왔거나 마지막 카드가 화면 아래 끝에 닿았고, 보이는 카드의 미리보기가 모두 그려짐)과 **전체**(카드가 모두 들어오고 읽기 끝)를 나눴다. 이전 버전은 카드를 한 번에 그려 둘이 같은 순간이다. 원자료: [qa/2026-10-08-perf-316.json](qa/2026-10-08-perf-316.json)(production, 5회, 다시 잰 반복 0회).

| 시나리오 | 첫 화면 (#315 뒤 → #316 뒤) | 전체 (#315 뒤 → #316 뒤) |
|---|---|---|
| S2 100 · 100 | 194 → **163** | 194 → 189 |
| S4 100 · 1000 | 538 → **492** | 538 → 600 |

- **효과는 작다.** #315 뒤 첫 화면 시간의 대부분은 보이는 카드(1600×1000 창에서 약 40장)의 미리보기 렌더라, 파싱·검증을 뒤로 미뤄 얻는 몫이 크지 않다. S4에서는 첫 화면이 9% 빨라지는 대신 전체가 11.5%(62ms) 늦다(묶음마다 목록을 다시 그리고 프레임을 기다린다).
- 묶음 크기를 비교했다(5회 중앙값, 원자료는 마지막 설정만 남겼다): 12개씩이면 S4 첫 화면 405ms·전체 687ms, 첫 24·뒤 50이면 490·594ms, 첫 묶음을 첫 화면 카드 수(42)로 하면 492·600ms. 12개 묶음 대비 지금 설정은 첫 화면을 약 85ms 내주고 전체를 약 90ms 아낀다. 첫 묶음 24와 42 사이는 첫 화면이 거의 같아(490·492ms), 첫 화면 시간의 큰 몫은 파싱이 아니라 보이는 카드의 미리보기 렌더로 보인다. 전체 손해(S4 +62ms, 11.5%)를 줄이는 쪽을 골랐다.
- **유지 여부는 머지 때 판단할 만하다.** 첫 화면이 S2 16%·S4 9% 줄고 전체는 S4에서 약 60ms 늦다. 대가로 로딩 상태·읽기 세대·요청 취소가 늘었다(이 작업에서 테스트 5개 추가).
- 홈에 남은 큰 비용은 보이는 카드의 미리보기 렌더다. 더 줄이려면 미리보기 자체(썸네일 등, #315에서 보류)를 다시 봐야 한다.

## 후속 4(#317) 측정 — 실제 입력 경로

#317은 "먼저 실제 입력 경로로 잰 뒤, 프레임 누락이 확인되면 렌더 범위를 줄인다"였다. 측정 스크립트에 `--input`을 더해 쟀다. 원자료: [qa/2026-10-08-perf-317.json](qa/2026-10-08-perf-317.json)(production, 5회, 다시 잰 반복 0회, 반복별 값 포함).

- **텍스트 삽입:** `t0`을 선택하고 속성 패널 "텍스트" 칸에 커서를 둔 뒤 30자를 `Input.insertText`로 넣는다. 텍스트 삽입(`beforeinput`/`input`)이고, keydown·IME 조합은 거치지 않는다. 넣은 뒤 내용이 실제로 바뀌었는지(`typing.applied`) 확인한다.
- **드래그:** 카드 `c1`을 선택하고 캔버스에서 `c3` 위치로 20단계 끈다. 놓은 뒤 스펙이 실제로 바뀌었는지(`drag.moved`) 확인한다. 처음에는 끌 대상이 바깥 섹션으로 잡혀 옮겨지지 않았고, 그 측정은 버렸다.
- 그동안 두 가지를 모은다.
  - `requestAnimationFrame` 간격: 놓친 vsync 수 = 간격이 16.7ms의 몇 배인지에서 1을 뺀 값의 합
  - Event Timing: 처리와 화면 반영이 16ms 이상인 입력 이벤트, 8ms 단위. `mousemove`·`pointermove`는 Event Timing 대상이 아니라 빠진다.

| 시나리오 | 텍스트 삽입: 놓친 vsync(반복별) | 텍스트 삽입: 입력 이벤트 p95 / 최대 | 드래그: 놓친 vsync(반복별) | 드래그: 누르기·떼기 등 p95 / 최대(반복별 범위) |
|---|---|---|---|---|
| S1 노드 100 | 0,0,0,0,0 | 16 / 16ms | 0,0,0,0,0 | 16 / 16~24ms |
| S3 노드 1000 | 0,0,**1**,0,0 | 24 / 24ms | 0,**1**,0,0,0 | 16~48 / 40~56ms |

**결론: 노드 1000개에서 가끔 한 프레임을 놓치지만, 지금은 렌더 범위 줄이기(노드 단위 memo·구독 분리)를 하지 않는다.**

- S3에서 텍스트 삽입·드래그 10회 중 2회가 vsync를 한 번 놓쳤다. (같은 방식의 앞선 실행도 비슷했으나 그 원자료는 이 측정으로 덮어썼다.) 30자 삽입이나 20단계 끌기 동안 한 번이라, 연속 입력이 끊겨 보일 수준은 아니다.
- 입력이 화면에 반영되기까지는 텍스트 삽입이 p95 24ms다. 드래그의 누르기·떼기(놓을 때 `moveNode`가 도는 쪽)는 최대 56ms다. 사람이 지연을 느끼기 시작하는 100ms 안팎보다 낮다.
- 그래서 이슈의 조건(프레임 누락으로 체감 문제가 확인됨)에 이르지 않았다고 판단한다. 연속 입력에서 끊김이 보고되면 `--input`으로 다시 잰다.

**재지 못한 것**

- **드래그 이동 중 지연:** 끄는 동안 마우스 이동마다 도는 처리의 지연은 Event Timing에 없어 재지 못했다. 위 드래그 이벤트 수치는 누르기·떼기 등만 반영한다. 프레임 간격(위 표)이 이동 중 끊김의 간접 근거다.
- **실제 입력 간격:** 텍스트 삽입·마우스 이동은 DevTools 프로토콜로 차례로 보내므로, 앞 입력의 처리가 끝나야 다음이 간다. 실제 간격은 처리 시간 + 16ms다. 처리 시간은 S3 텍스트 삽입이 약 22ms, S1이 약 5ms다. 처리보다 빠르게 몰아치는 입력은 재지 않았다.
- **keydown 처리:** 키 입력의 keydown 처리(전역 단축키 판정 등)와 한글 IME 조합은 재지 않았다.
- **다른 연속 편집 경로:** 숫자 필드 스크럽처럼 다른 연속 편집 경로도 재지 않았다.
- 프로파일상 편집 한 번의 남은 비용(production)은 `useStore`(zustand 구독) 약 5%, DOM 갱신 약 11%, 자동 저장 복구 사본 쓰기 약 3%다(위 "병목 근거").

## 그 밖의 관찰

- **메모리 누수 여부는 판단하지 않았다.** GC를 강제한 뒤 재면 S3에서 편집·Undo 10회와 Export 뒤 힙이 열기 직후보다 약 11~20MB 크다(production 29 → 41MB, 개발 40 → 60MB). 편집 직후 Undo하므로 히스토리에는 스냅샷이 최대 하나뿐이라 히스토리 때문이라고 볼 수 없다. Export 단계에서 처음 불러오는 모듈, 측정 도우미, 자동 저장 직렬화 등이 섞여 있어 원인을 가르지 않았다. 한 번의 측정으로 누수가 없다고도 말할 수 없다. 에디터로 들어가면 홈 DOM은 정리된다(S4 DOM 17만 개 → 2.5만 개).
- **production 번들**은 `pnpm build` 기준 JS 548.30kB(gzip 165.64kB)이고 500kB 경고가 난다. 이슈 작성 당시 533.46kB에서 늘었다. 지금 사용자는 개발 서버로 GUI를 쓰므로 이 번들을 받지 않는다(우선순위 5 — #314 뒤에도 그대로).
- **큰 이미지**는 홈 카드 측정 시점(카드 DOM 완료)·열기(두 프레임)·JS 힙에 차이가 없었다. 이미지는 CSS 배경(`ui/homePreview.ts`·`ui/nodeStyles.ts`)으로 비동기 로드되므로 다운로드·디코딩(2400×1600이면 비트맵 약 15MB)·그리기는 재지 않았다. 판단은 후속 6의 추가 측정까지 보류한다.
- 노드 100개 문서의 편집·Undo는 "다음 태스크까지 경과"가 4~14ms로 노드 1000개보다 훨씬 작다. 이 측정만으로 프레임 안에 든다고 단정하지는 않는다 — 우선순위를 정하는 신호로 쓴다.

## 한계

- 한 기기(Apple M5)의 헤드리스 Chrome 값이다. 더 느린 기기에서는 비례해 커질 것으로 보지만 재지 않았다.
- 편집은 스토어 액션을 직접 불러 쟀다. 속성 패널 입력·캔버스 드래그 같은 실제 입력 경로의 이벤트 처리는 포함하지 않는다.
- #293 측정 당시 `NODE_ENV=production` 개발 서버는 비교용 실험이었고 GUI 전체 기능은 확인하지 않았다. #314에서 이 모드를 사용자 기본으로 바꾸며 주요 흐름을 확인했고, 사라지는 것(Fast Refresh·StrictMode 이중 실행·자세한 오류 문구)을 "후속 1 적용 뒤"에 적었다.
- Export는 빈 컴포넌트 파일로 쟀다. 실제 생성 코드가 크면 검증(import 훑기) 시간이 늘 수 있다.

## 다시 재는 방법

```bash
# 저장소 루트에서. Chrome 경로는 자동으로 찾고, 없으면 --chrome 또는 CHROME_BIN.

node scripts/perf/measure.mjs --reps 1 --scenario S3,S4 --profile --json prof.json  # 병목 프로파일(별도 반복)

```

표의 원자료는 이 문서의 스크립트로 쟀다. 그 뒤 리뷰에서 스크립트의 견고성(DevTools 연결 끊김·시간 초과 처리, 포트 충돌 방지, 개발 서버 조기 종료 감지)과 프로파일 반복 분리를 고쳤다 — 프로파일을 켜지 않은 측정의 타이밍 경로는 바뀌지 않았다.

시나리오마다 임시 폴더에 작업공간을 만들고, 빈 포트로 개발 서버와 헤드리스 Chrome을 띄운 뒤 끝나면 지운다. 다섯 시나리오 5회는 이 기기에서 모드당 약 10분 걸린다.
